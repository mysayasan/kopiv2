# Module: apps/myidsan/services/session.go

## Purpose

Session administration: `ISessionService` records, lists, and revokes SSO sessions.

## Responsibilities

- The cache entry at `sso:session:<sid>` remains the AUTHORITY: the auth middleware checks
  it on every request, and deleting it is what actually ends a session. This service keeps
  a `domain/entities.UserSession` row (`domain/entities/user_session.go.md`) alongside each
  one purely as an INDEX, because the cache is keyed by session id and cannot answer "which
  sessions does this user have?" — the question an administrator revoking access, and a
  user reviewing their own devices, both need answered.
- `Record(ctx, s)` persists a newly issued session (best-effort: a failure to index must
  never fail the sign-in that just succeeded).
- `Touch(ctx, sessionId)` refreshes `LastSeenAt`.
- `ListForUser(ctx, userId, currentSessionId)` returns `[]SessionView` (id, session id,
  user id, IP, user agent, created/last-seen/expires timestamps, `Active`, `Current`),
  newest first, **reconciled against the cache** — filters on the `UserLoginId` FK with an
  explicit `Equal` rather than `GetByForeign`, which is hardcoded to a single child row.
  `Active` is true only when the row is unrevoked, unexpired, AND its cache entry still
  exists (`isLive`); a row alone never proves a live session, so a session that simply
  expired stops appearing as usable without anything having called `Revoke`. A cache read
  error falls back to the row's own state rather than telling a user a live session has
  ended (fail open on cache trouble, since telling a user "this device is signed out" when
  it is not misleads them more than the reverse).
- `Revoke(ctx, sessionId)` ends one session: **deletes the cache entry FIRST**, then marks
  the row (`RevokedAt`, `IsActive = false`) second. If the row update fails the session is
  already dead, which is the safe direction to fail in — doing it the other way round would
  leave a row claiming "revoked" while the session still worked.
- `RevokeAllForUser(ctx, userId, exceptSessionId)` lists, then revokes every currently-live
  session except the one named (used for "sign out everywhere else"), returning a count.
- `CountActive(ctx)` counts rows the INDEX still marks active (an `IsActive = true` filter
  on the repo), backing the `myidsan_sessions_active` gauge (`services/metrics.go.md`). It
  reads the table, not the cache — the cache remains the authority on whether any one
  session is valid, but it cannot be enumerated, so a fleet-wide count has to come from the
  table. The two can differ briefly (a cache entry that expired on its own leaves its row
  still marked active until something reconciles it), which makes this a capacity/anomaly
  signal rather than an exact live count. Covered against a real bootstrapped SQLite
  database, not just the package's hand-written fake repo
  (`services/session_sqlite_test.go`): the filter is on a **boolean** column, and the query
  builder renders bool filter values as quoted literals, which a fake repo — comparing Go
  values, so it agrees with whatever was assumed — cannot catch a mismatch on. A mismatch
  there would make the gauge read a permanent zero indistinguishable from "no sessions".
- Package-level `PublishActiveSessions(ctx, sessions ISessionService, m telemetry.Metrics)`
  sets the gauge from one `CountActive` call; nil-safe on either argument. Kept separate
  from `CountActive` so the scheduler task that calls it (`startSessionGauge`,
  `app/audit_retention.go.md`) is a one-liner and the count stays testable without a
  metrics recorder. Polled on a timer rather than incremented at `Record`/`Revoke` call
  sites, because sessions also end without anyone calling `Revoke` — a cache entry simply
  expires — so a hand-maintained counter would drift from the truth and never recover; a
  periodic read of the index cannot drift, it is at worst one interval stale.

## Notes

- `SessionView.Current` lets the UI label and warn before someone signs themselves out;
  set from the caller-supplied `currentSessionId`, which comes from the request's own JWT
  claims (`session id`), never trusted from the client body.
- Session ids are pre-generated by the login API (`apis/login.go.md`'s
  `issueSessionCookies`) specifically so this service can index the session as it is
  issued — `AuthMidware.IssueAuthCookies` mints its own id only when the field is empty and
  never reports it back.
- Consumed by `apis/session.go.md` (self-service + admin routes) and
  `apis/user_login.go.md` (`endSessionsFor`, ending sessions on disable/delete).
