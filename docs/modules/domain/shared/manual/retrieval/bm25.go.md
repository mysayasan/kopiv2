# Module: domain/shared/manual/retrieval/bm25.go

## Purpose

The ranking function: an in-memory BM25 index over one language's chunks (`index`, built once by
`buildIndex`, then read-only).

## Why BM25 is the right tool and not a compromise

The corpus is a few hundred hand-written sections. The classic ranking function needs no model, no
download and no store, answers in microseconds, and above all is **deterministic** — the golden
tests can assert that a given question retrieves a given section, which is not something an
embedding model lets you promise across a version bump.

Constants: `bm25K1`=1.2, `bm25B`=0.75.

## The topic boost (and the repetition scheme it replaced)

The one departure from textbook BM25. A section *titled* "Discovery" is about discovery in a way
that a paragraph mentioning the word once is not, so a query term found in a chunk's **heading,
article title, slug or category** adds `topicBoost`(1.5) × its IDF, on top of the ordinary BM25
term score.

The first implementation instead repeated title terms 2–3× into the term stream. **A live bench
showed that does not work**: BM25's term-frequency saturation (k1=1.2) turns a 3× repeat into
roughly a 1.7× score, so the title signal drowned in body text and `how do I add a camera` ranked
a disk-sizing FAQ answer above the article literally titled "Adding cameras". Scoring the topic
fields as a separate additive term keeps them out of the saturation curve and out of the length
normalisation entirely.

Topic terms are still *indexed* (at plain weight) — otherwise a term appearing only in a heading
would never make its chunk a search candidate — but their pull comes from the boost at query time.

## IDF, and the price of an unknown word

`idf = max(0, ln(1 + (N-df+0.5)/(df+0.5)))`, floored at zero so a term in nearly every document
cannot *subtract* score from a document that legitimately contains it.

`maxIDF = ln(1 + (N-0.5)/1.5)` — what a term found in exactly one chunk would score — is the price
the index puts on a query term it has **never seen**. This matters more than it looks:
`Result.Coverage` divides matched IDF by the query's total IDF, and if unknown words counted as
zero, a question the corpus knows two words of would look *fully covered*. Measured symptom before
the fix: "what is the exchange rate for the yen" retrieved a camera-preview section, because the
manual happens to know the word "rate".

## Key Type: Result

```go
type Result struct {
    Chunk    Chunk
    Score    float64  // raw BM25 + topic boost
    Coverage float64  // matched IDF / total query IDF (unknown terms priced at maxIDF), 0..1
    TopicHit bool     // a query term is in this chunk's heading/title/slug/category
}
```

`Score` alone is meaningless as a threshold — its scale moves with corpus size and query length.
`Coverage` is scale-free, and `TopicHit` says *where* the match landed rather than how much of it
there was. `Corpus.Search` gates on **either**, and it needs both: measured, a valid Arabic
question scored 0.31 coverage while matching the article's own title, and a nonsense question
scored 0.48 off one body word. See `domain/shared/manual/retrieval/retrieval.go.md`.

What neither can do is distinguish a how-to question from a what-is-happening-now question — that
one is not a scoring problem, and the design absorbs it instead.

## Determinism

Ties break on `Chunk.ID()`, so the same question always produces the same citation order. A chat
answer that reorders its sources between identical runs reads as unreliable.
