# Module: infra/recording/rtsp.go

## Purpose

Implements the RTSP-mode per-camera recorder that runs a dedicated ffmpeg segmenter process and extracts MP4 clips from the rolling segment buffer on alert events.

## Responsibilities

- Run an ffmpeg process that writes the camera RTSP stream into rolling `.ts` segment files using the `-f segment` muxer with `-strftime 1` filename templating (`%Y%m%d_%H%M%S.ts`).
- Pass `-fflags +genpts` to ffmpeg to generate PTS from DTS for cameras that omit stream timestamps.
- Copy the video stream (`-c:v copy`) and transcode audio to AAC (`-c:a aac`) so all camera audio codecs (pcm_alaw/G.711, G.726, etc.) are muxed as a native MPEG-TS stream type without a private data stream warning.
- Pass `-af aresample=async=1` to compensate for cameras that send non-monotonic audio timestamps, preventing the `[aac] Queue input is backward in time` error.
- Filter known harmless ffmpeg warnings from `lastErrMsg` via `isNoisyFFmpegWarning` so the status panel shows only meaningful errors. Suppressed patterns include:
  - `Non-monotonic DTS`
  - `Timestamps are unset`
  - `This may result in incorrect timestamps`
  - `DTS discontinuity`
  - `starts with a non keyframe`
  - `is muxed as a private data stream`
  - `Queue input is backward in time`
  - `[segment @...]` address-only lines
- Restart ffmpeg automatically on unexpected process exit.
- `Start` runs `runFFmpeg`, `watchSegments`, and `purgeOldFiles` each under `infra/safego.Supervise` (names `recording.cam<N>.ffmpeg`/`.segments`/`.purge`) rather than a bare `go`. A panic in any of them used to take the whole process down; merely recovering would be no better, since nothing else would notice a dead segment watcher (the camera would keep writing `.ts` files that are never finalized) or a dead purge loop (the disk would fill) — so all three restart with backoff instead of just logging and exiting.
- After two consecutive quick failures (runtime < 10 s), toggle between `RTSPURI` (primary) and `FallbackRTSPURI` (fallback) to handle cameras that reject a second RTSP connection on the main stream. Fallback switching is transparent; the active stream URL is exposed via `CameraStatus`.
- Read ffmpeg stderr line-by-line with `bufio.Scanner` to avoid partial-line artefacts from raw `Read()` calls; the noisy-warning check runs before logging so filtered lines are never written to the log.
- List live `.ts` segment files and parse filenames as **local time** (`time.Local`) because ffmpeg `strftime` writes in the local timezone.
- On `TriggerEvent(alertId, frameCapturedAt)`: use `frameCapturedAt` as the clip anchor to compensate for YOLO inference latency; fall back to `time.Now()` when zero. Wait for post-roll, then select `.ts` segments covering `[frameCapturedAt − preRollSec, frameCapturedAt + postRollSec]`.
- Write a concat list and run a second ffmpeg pass with `-fflags +genpts`, `-ss`, `-t`, and `-movflags +faststart` to extract and remux the clip as MP4.
- Notify the `SegmentSink` with the resulting `SegmentResult`.
- Watch completed segments and remux each `.ts` to MP4, persist to the `SegmentSink`, and delete the source `.ts` only after the finished MP4 has been published. The remux is `-c copy` by default; when the at-rest storage codec is `h264`/`hevc` (`RecorderConfig.RecordCodec`) it re-encodes the video on the GPU via NVENC — prepending the hardware-decode input options and acquiring a slot from the shared NVENC semaphore (`infra/recording/encode.go`) so concurrent remuxes never oversubscribe the card; the `.ts` is already on disk, so waiting only delays finalize and never drops footage. The segment's on-disk codec is recorded on `SegmentResult.Codec` (known when re-encoding; probed via `probeVideoCodec` in copy mode). Live capture and event clips always stay stream-copy.
- **Crash-safe segment finalization** (`partSuffix = ".part"`): `remuxSegment` builds the finished MP4 at `<stem>.mp4.part`, and only `os.Rename`s it into place at `<stem>.mp4` *after* it has been encrypted (when at-rest encryption is on) — the source `.ts` is removed only once that rename succeeds. This makes a bare `<stem>.mp4` on disk unambiguous proof of a complete, encrypted segment, and a `.ts` sibling unambiguous proof the stem was never finalized. `Start()` calls `cleanStaleParts()` to remove any leftover `.part` file from an interrupted remux (its `.ts` is still on disk and will be re-remuxed, so the partial is pure garbage). Previously the remux wrote directly to `<stem>.mp4`; an interrupt left a truncated file that `saveCompletedSegments` then adopted as canonical footage (only guard was `size > 0`), abandoning the intact `.ts` to the retention purge — silent footage loss — and that adoption path never encrypted the file, so it also sat plaintext at rest.
- **`-f mp4` is mandatory on the remux command, not defensive.** ffmpeg selects the output container from the file extension, and `.part` is not a container it recognises — without an explicit `-f mp4` it aborts every segment with `Unable to choose an output format`. Any change to `partSuffix` or to the finalize output path must keep an explicit output format. (Input probing is unaffected: `segmentEndedAt`/`probeVideoCodec` read the `.part` by content sniffing, not extension.)
- **Per-stem finalize bookkeeping** (`claimStem`/`finishStem`, guarded by `segMu`): `segBusy` stops the 5 s watch tick from launching a second remux for a stem already in flight; `segDone` marks a stem persisted or deliberately discarded; `segFails` counts consecutive failures. A stem is *not* marked done until its finalize attempt actually succeeds (previously it was marked saved before the remux ran, so any failure stranded it permanently with no retry). `remuxOutcome` (`remuxSaved`/`remuxDiscarded`/`remuxFailed`/`remuxUnsaved`) drives bookkeeping: `remuxUnsaved` (file finalized on disk, only the sink write failed) and a cancelled context don't burn a retry attempt.
- **Quarantine**: after `maxRemuxAttempts` (3) consecutive failures, `finishStem` calls `quarantineSegment`, which moves the source `.ts` to `quarantine/` (a sibling of `live/`, under `{storagePath}/cam{cameraId}/`) instead of leaving it in `live/` where the retention purge would silently shred footage that was never saved, and stops retrying so the stem can't respawn ffmpeg forever. `purgeOldFiles` calls `purgeQuarantine(cutoff)` each pass so quarantined `.ts` files still age out under the camera's normal retention (via `SecureRemove`), rather than accumulating forever on a persistently failing camera.
- **`adoptSegment`**: the restart-time path for a bare `.mp4` with no `.ts` sibling (a segment a previous run finished but never persisted, or whose DB save failed). It probes/persists the file, and — as a legacy safety net for segments finalized by an older build (which encrypted *after* publishing, so an interrupted run could leave one plaintext) — encrypts it in place first if it's plaintext and encryption is on. It never runs ffprobe on an already-encrypted file (ffprobe cannot read ciphertext, and probing every encrypted live-dir file on the first tick after a restart would be a process storm for a result that's always discarded).
- `Close()` waits (bounded by `remuxDrainTimeout` = 10 s) for all in-flight remuxes on that recorder to finish via `remuxWG`, so `Manager.Configure` closing the old recorder and immediately starting a new one on the same live directory can't race two ffmpeg processes onto the same output file. Cancelling the recorder context kills the child ffmpeg, so in practice this returns in milliseconds.
- `remuxSegment` now runs bounded by the **recorder's** context (`ctx, cancel := context.WithTimeout(ctx, 10*time.Minute)`), not `context.Background()`, so a shutdown or reconfigure tears the child ffmpeg down instead of orphaning it for up to 10 minutes against a live directory a freshly-started recorder now owns. Persisting to the sink still uses a short-lived context detached from the recorder (`context.WithoutCancel`) so a segment that finishes finalizing during shutdown is still saved rather than orphaned.
- **Codec fallback** (`RecorderConfig.RecordFallbackCopy`, default on): before building the remux command, if the configured codec re-encodes and `NVENCUsable` reports the encoder doesn't run on this host (no usable NVIDIA GPU/driver), the segment is proactively downgraded to plain stream-copy for that remux — no wasted ffmpeg attempt. If a re-encode is attempted (the up-front probe passed) but still fails at runtime (a transient driver/session issue), the segment is retried once as stream-copy instead of being dropped; `SegmentResult.Codec` is then probed from the copied stream rather than assumed. When fallback is disabled, a failed re-encode still drops the segment and logs the error (previous behaviour).
- Expose `CameraStatus` including `state`, `ffmpegRunning`, `liveFiles`, `liveDir`, `lastError`, `activeStreamUrl`, `usingFallback`, ring-buffer frame count, and ring-buffer capacity.

## Notes

- `WriteFrame` is a no-op in RTSP mode; frames are consumed directly by the ffmpeg subprocess.
- The `quarantine/` directory only ever appears once a segment has failed to finalize `maxRemuxAttempts` (3) times in a row; its presence is a signal worth an operator's attention (a persistently corrupt/unreadable `.ts`), though the footage inside it is preserved and still ages out under normal retention.
- AAC audio transcoding adds negligible CPU compared to video copy.
- `aresample=async=1` resamples audio to match timestamps when the camera sends them out of order, absorbing backward jumps before the AAC encoder sees them.
- **Timezone invariant**: segment filenames are written in local time by ffmpeg `strftime`. Both `listLiveSegments` calls use `time.ParseInLocation(..., time.Local)` — never `time.UTC`.
- The live segment directory is placed under `{storagePath}/cam{cameraId}/live/`; extracted clip files are placed under `{storagePath}/cam{cameraId}/clips/`.
- Diagnostic `log.Printf` lines in `extractClip` log the clip window and all available segments with local times to aid debugging when a clip is not found.
