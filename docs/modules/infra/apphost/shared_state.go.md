# Module: infra/apphost/shared_state.go

## Purpose

States, once at startup, whether this process's session state is visible to other instances of itself — so a load-balanced multi-instance deployment that is silently single-instance-only reads as a config problem in the boot log, not as "flaky sign-ins" reported by users later. Now reads the operator's DECLARED deployment mode (`domain/shared/services.DeploymentModeKey`, set from the setup wizard's Deployment step or the Settings panel) so the loud branch can state a fact rather than infer one.

## Responsibilities

- `declaredDeploymentMode(dbCrud dbsql.IDbCrud) string` — reads the persisted `deployment.mode` `RuntimeSetting` row (via `sharedServices.NewDeploymentModeService(repo).Get(ctx)`), bounded by a 3-second timeout (`declaredDeploymentModeTimeout`) so a slow or not-yet-existent table can never delay boot. Returns `""` (undeclared) on any failure, on a nil `dbCrud`, or when the row has never actually been written (`state.UpdatedAt == 0` — `Get()` reports an absent row as standalone, which is the right default for a normal reader but would misreport a never-asked install as an explicit answer here). Runs **before** schema is guaranteed to exist (a first boot may have no `runtime_setting` table yet), which is why every failure is silent rather than logged — a scary error on every clean first boot would be noise that makes the real warning easy to ignore.
- `warnSharedStateBoundary(cacheProvider, lockProvider, declaredMode string)` — called from `runApp` (`run.go`) right after the transaction-lock provider log line, with the already-resolved cache/lock provider names and `declaredDeploymentMode(dbCrud)`:
  - **`declaredMode == ModeClustered`** (operator explicitly said multi-instance): a per-process cache is now a hard `WARNING` — sessions are held in the cache, so a second instance will not recognise this one's sessions and users are signed out whenever the load balancer moves them. If the cache is shared but the transaction lock is not, a second `WARNING` names that instead — scheduled work (retention purges, rollups, digests) will run once per instance. Only when both are shared does it log a plain confirmation that this instance can run behind a load balancer. These are no longer inferences from a contradiction; they are stated as facts because the operator already answered the question.
  - **`declaredMode == ModeStandalone`** (operator explicitly said single-instance): logs plainly, with no alarm, even on a per-process cache — that is the intended, supported configuration for a declared single instance.
  - **Undeclared** (`declaredMode == ""` — every pre-wizard install, and every app during first boot before the wizard has run): falls back to the previous inference-only behavior — `isSharedCacheProvider(cacheProvider)` true logs that sessions survive a restart and are visible to every instance; otherwise `isDistributedLockProvider(lockProvider)` true logs a `WARNING` for the self-inconsistent pairing (distributed lock + per-process cache); otherwise logs plainly that the cache is per-process and this instance is single-instance only.
- `logSigningSecretFingerprint(secret, cacheProvider, lockProvider, declaredMode string)` — called from `runApp` immediately after `warnSharedStateBoundary`, with the resolved `appConfig.Jwt.Secret`. Prints a one-way fingerprint (`atrest.FingerprintSecret`, see `infra/atrest/cipher.go.md`) of the signing secret so an operator can confirm two instances hold the SAME one. This is the ONLY check available: every instance must share a signing secret or a token minted by one is rejected by the next — which presents as users randomly signed out rather than as a configuration error — and no process can tell from the inside, because a secret the host generated is written back to that instance's own config file and looks configured from the next boot onward.
  - Deliberately the LOG rather than the deployment checklist: a `jwt.secret` only has to clear a 16-character floor (`run.go.md`'s `isWeakJWTSecret`), so an operator may legitimately hold a weak one, and publishing a fingerprint of it to every signed-in user would hand out something to attack offline for a token-forging key. Logs are already operator-only, and an operator comparing two instances is reading both hosts anyway. The checklist's `jwtSecret` row reports provenance (generated vs. configured) instead.
  - Printed only when more than one instance is plausible — `declaredMode == ModeClustered`, or a shared cache, or a distributed lock. A genuinely standalone install has nothing to compare against, and a line that means nothing to most installs is one everybody learns to skip, which costs the warnings that matter. Empty secret prints nothing.
- `isSharedCacheProvider(provider)` / `isDistributedLockProvider(provider)` are gone from this file — both are now the single shared functions `sharedServices.IsSharedCacheProvider`/`IsDistributedLockProvider` (`domain/shared/services/deployment.go.md`), exported so this boot warning and the deployment preflight checklist can never disagree about which provider strings count as shared.

## Notes

- Sessions live in the cache and the cache is the authority on session validity (see `docs/DB_BOOTSTRAP_SPEC.md`'s note that live session validation uses the configured cache provider, not a DB table); with the in-process memory cache that authority is per-process, which is the entire reason this exists.
- Before a declared mode existed, the loud branch was necessarily a contradiction check rather than a direct statement: there is no reliable way for a process to detect "am I one of several replicas" from the inside, so a warning that fires on healthy single-instance installs is one operators learn to ignore. A distributed transaction lock was the one config signal that already said "more than one instance is expected." With a declared mode (persisted by the setup wizard/Settings panel) the boundary can now be stated as a fact for the two apps that support declaring it (`myseliasan`, `myidsan`); the contradiction check remains the fallback for every undeclared install and for the three appliance apps, which never expose a way to declare `clustered` in the first place (see `domain/shared/services/deployment.go.md`'s tiering).
- Applies to every app (`mymatasan`, `myseliasan`, `myidsan`, `myiotsan`, `mypintusan`) — this is shared `infra/apphost` wiring, not identity/myidsan-specific, even though the productization plan that motivated it (`docs/MYIDSAN_PRODUCTIZATION_PLAN.md` §4.2) is myidsan's.
