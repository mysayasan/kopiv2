# Technical Specification

## Scope

`kopiv2` is a Linux-first, lightweight Go backend that provides:

- HTTP API with cookie-backed JWT auth and RBAC enforcement.
- Standalone ONVIF device discovery and RTSP stream probing for camera setup.
- Reusable visual detection primitives for camera rules, rule-level schedules, motion detection, external object detection, persistent object workers, line crossing, multi-line crossing, crowd detection, license-plate recognition (LPR), face recognition (enroll/recognize against a global gallery), hybrid dispatch, and alert events.
- SQL persistence using a generic repository layer.
- Static SPA serving from app assets.
- Public runtime version reporting with separate core and app SemVer values.
- A dedicated identity app (`myidsan`) for user management, RBAC administration, and planned SSO authority.

The runtime now uses a reusable multi-app launcher pattern:

- root launcher: `main.go` with `-app <name>`
- shared startup/runtime host: `infra/apphost`
- per-app compile target: `cmd/<app>/main.go`

## Runtime Targets

- Primary: Linux hosts (including low-resource deployments).
- Container runtime: Docker and Docker Compose.
- Service runtime: systemd unit supported in `deploy/linux`.

## Runtime Characteristics

- Go version: `1.26.4`.
- App selection:
  - runtime selection via `go run . -app <name>`
  - compile selection via `go build ./cmd/<name>`
  - currently registered apps: `mymatasan`, `myidsan`, `myseliasan`, `myiotsan`
- **Shared frontend module** (`frontend/shared/`): plain ESM, no build step; consumed by both myidsan and myseliasan via a `@shared` webpack alias + `resolve.modules` entry in each app's `webpack.config.js`. Exports: `DataTable`, `Toast`/`ToastStack`, `SideNav` (brand/footer slots + bespoke item injection via a `render` hook — myseliasan injects its Nodes tree), and `icons` (`Ico` + `icoSvg` union). Theming via `--ui-*` design tokens each app maps to its own palette. Per-app copies (`data_table.js`, `icons.js`) have been deleted from both apps. Three themes are supported in both SPAs: Light, Dark, and **High contrast** (black surfaces, white text, bright accents, strong borders). Side-nav colors follow the active theme via `--nav-*` tokens.
- HTTP server defaults:
  - Read header timeout: `5s`
  - Read timeout: `15s`
  - Write timeout: `30s`
  - Idle timeout: `60s`
- Graceful shutdown on `SIGINT` and `SIGTERM`.
- Version manifest: embedded from `infra/versioning/version.json` at build time.
- **Background-goroutine panic resilience** (`infra/safego`): apps that run unattended background workers (samplers, monitors, ticker-driven purges) start them via `safego.Go` (one-shot; panic recovered and logged, not restarted) or `safego.Supervise` (long-lived loops; panic recovered, logged, and the loop restarted with backoff — 1s initial, doubling, 30s cap, resetting after 2 minutes of healthy runtime). A clean return from a supervised task is treated as a deliberate stop and is not restarted. `mymatasan` wires `safego.SetLogger` to its app logger at the top of `RegisterAppRoutes` and supervises its vision monitor, per-camera samplers, camera/machine health monitors, metadata recorder, RTSP recorder goroutines, the discovery responder, the three node-dialed fleet channels (enrollment/control/media — previously bare `go` calls), and retention purge loops — started from `apps/mymatasan/app/wire_monitors.go`, see `apps/mymatasan/app/app.go.md` and `apps/mymatasan/app/wire_monitors.go.md`.

## Security Model

- Authentication: JWT session stored in an HttpOnly cookie.
- CSRF protection: unsafe authenticated methods (`POST`, `PUT`, `PATCH`, `DELETE`) require `X-CSRF-Token` matching the readable CSRF cookie.
- **CSRF on the server-rendered auth forms** (Productization Phase 3): `/api/auth/{login,mfa,forgot,reset}` are public routes reached before any session exists, so they never pass through the auth middleware's session-bound CSRF check and previously had none at all — a gap that allowed login-CSRF/session-fixation and a forced password-reset submission on behalf of a signed-in-elsewhere victim. Each render now mints a session-less double-submit token (`apps/myidsan/apis/auth_form_csrf.go`): a random value set as a cookie (`__Host-`-prefixed over TLS) and embedded as a hidden form field; the POST handler rejects the submission unless the two match. The token must be minted before `WriteHeader` — a cookie set from inside the `Fprintf` argument list is silently dropped once the status line is written, since `http.SetCookie` only appends to the (already-flushed) header map.
- **Relying-app client secrets are hashed with bcrypt** (Productization Phase 3; previously unsalted single-round SHA-256, so a read of `app_auth_config` handed an attacker every operator-chosen client secret at GPU speed). `secretMatches` accepts both the current bcrypt form and the legacy SHA-256 form and reports whether the row needs rewriting; `POST /api/auth/token` rewrites a legacy row to bcrypt the first time its secret is presented, so an existing install migrates itself without an operator re-entering any client secret.
- Local credential auth endpoints are available under `/api/login/default` (login) and `/api/login/default/register` (register) in `myidsan`; relying/resource apps do not mount login APIs.
- Federated login providers are optional and do not disable local credential auth when not configured. Each redirect-style provider implements `infra/login.RedirectProvider` and is admitted into a shared `infra/login.Registry` only when configured — for Google/GitHub, `client_id`/`client_secret` (after config + env) both non-empty; a blank block is **disabled with a warning** rather than blocking startup. One generic route pair, `GET /api/login/{provider}` and `GET /api/callback/{provider}`, serves every registered provider (no more one hardcoded route pair per provider). The federated login page (`GET /api/auth/login`) renders a button per provider currently in the registry; the SPA reads the same set from `GET /api/login/providers` (`{list: [{key, displayName, kind}], google: bool, github: bool}` — the boolean fields are a legacy shape kept for older SPA builds). A federated callback resolves to a local account via `services.UpsertFederated`, which matches strictly on `(provider, subject)` — never on email alone, closing an account-takeover path where a same-email account at a different provider could previously be silently merged into an existing one; a same-email account with no identity bound yet may still claim one, once.
- **LDAP/Active Directory login** (`docs/MYIDSAN_ENTERPRISE_SSO_PLAN.md` Phase 1; live-bench-tested against a real OpenLDAP 2.4 server over both LDAPS and StartTLS — `infra/login/ldap_integration_test.go`, gated on `RUN_LDAP_IT=1`; not yet tested against Active Directory or Samba AD specifically): a credential check, not a redirect provider (`infra/login/ldap.go`, `github.com/go-ldap/ldap/v3`, pure Go) — service bind, single-entry search from a `%s`-templated, filter-escaped user filter (ambiguity or a filter-injection attempt both fail closed), then a bind AS the user; transport is always TLS (`ldaps` or `StartTLS`, optional pinned CA), and an empty/NUL password is refused before any network I/O (many servers treat that as a successful anonymous bind). Settings live in a new DB-backed singleton `DirectoryConfig` (bind password encrypted at rest via `infra/atrest`, myidsan's first at-rest-encrypted secret) managed from Federation → Directory, with a "Test connection" probe that validates the submitted (unsaved) settings and never binds as the sample user. A `FederatedGroupMapping` table maps a directory group (AD group DN, matched case-insensitively; highest `Priority` wins) to a myidsan role — a `DirectoryConfig.Authoritative` toggle decides whether the mapping re-applies on every login or only seeds a still-pending account once, and no match leaves the account's role untouched (pending clearance stands). `POST /api/login/ldap` (SPA) and a `method` field on the server-rendered `/api/auth/login` form (an "Account type" select, rendered only while directory login is enabled) both authenticate through the identical `services.IDirectoryService.AuthenticateLdap`, which reuses the same `UpsertFederated` strict `(provider, subject)` dedup as Google/GitHub.
- **Per-IP *and* per-account failed-login lockout** (Productization Phase 3): the shared `sharedapis.LoginGuard` (the same primitive `mymatasan`/`myiotsan` use, config block `loginSecurity`) now guards `POST /api/login/default`, `POST /api/login/ldap`, and the server-rendered `/api/auth/login` POST on **two** keys — `ip:<remote addr>` and, once the request body is decoded, `user:<lowercased identifier>` — so a password spray distributed across many source addresses against one account is throttled, not just a single IP hammering many accounts. The lockout check moved to after body decoding so the account key is available. Tradeoff, accepted deliberately: an attacker who knows a username can now lock that account out; that is a recoverable nuisance (wait out the window, or a successful sign-in clears both counters) versus unlimited credential guessing against a known account, which is not recoverable. Token-based steps (MFA code redemption, the forgot-password request) stay keyed on source IP only — they present a challenge token or an unproven identifier, not a password. `GET /api/login/kerberos` deliberately does not consult this guard — a Kerberos ticket is cryptographically verified, not guessed.
- **Password policy** (Productization Phase 3, config block `passwordPolicy`): a configurable minimum length (default 12, up from the previous hard-coded 8), optional character-class requirements (upper/lower/digit/symbol — default OFF, to avoid pushing users toward predictable `P@ssw0rd1`-style substitutions), an embedded common-password denylist (default ON — no HIBP lookup, since myidsan is positioned to run air-gapped), and a same-as-username rejection. Enforced at all four paths that ever set a human-chosen password — self-registration, admin-provisioned account creation (`POST /api/user-credential`, previously unchecked beyond non-empty), authenticated change-password, and self-service token-based reset — via `apps/myidsan/services.ValidatePassword`. Server-generated credentials (bootstrap/temporary passwords, 16-character CSPRNG output) are exempt by design.
- **Kerberos SPNEGO SSO** (`docs/MYIDSAN_ENTERPRISE_SSO_PLAN.md` Phase 2; **live-benched against a real Samba AD DC, realm `KOPI.TEST`, 2026-07-29**): `GET /api/login/kerberos` verifies a domain-joined browser's `Authorization: Negotiate` service ticket against an exported keytab (`infra/login/kerberos.go`, `github.com/jcmturner/gokrb5/v8`, pure Go) — a bare request gets a `401` + `WWW-Authenticate: Negotiate` challenge, never a hard error, so the browser can retry with a ticket. A verified principal resolves through `services.IDirectoryService.ResolveDirectoryUser` (an LDAP service-bind search with **no user bind** — Kerberos already proved identity) to the same account/group→role mapping a password or LDAP login for that person reaches; without a directory configured, a principal-derived standalone identity is used instead. Any failure (rejected ticket, disallowed realm, unresolvable principal) redirects the browser to `/api/auth/login?error=sso_failed` with an inline message — never a dead-end `401` body — and is counted in `myidsan_federated_login_total{provider="kerberos",result=...}`. Configured via a new `kerberos` config block (`enabled`, `keytabPath`, `servicePrincipal`, `onlyRealms`, `displayLabel`); a bad/missing keytab logs a warning and disables Kerberos rather than failing startup. **The bench found and fixed the same gap as the OIDC bench below**: a rejected ticket had been recorded only as a metric, never in the audit trail. Every rejection path in `kerberosLogin` now also calls `recordKerberosLoginFailure` (`apps/myidsan/apis/login.go`), recording `login.failure` with `{method: "kerberos", provider}` metadata; the no-token challenge path deliberately does not audit (it is the first half of every SPNEGO handshake), and Kerberos failures deliberately do not advance the `LoginGuard` lockout (a ticket is cryptographically verified, not guessed). See `docs/HOWTO.md`'s Kerberos SSO subsection for keytab provisioning and operational requirements.
- **Generic OIDC login** (`docs/MYIDSAN_ENTERPRISE_SSO_PLAN.md` Phase 3; **live-benched against a real Keycloak 26 realm, 2026-07-29**): each entry in the new `login.oidc[]` config array (`infra/login/oidc.go`, `github.com/coreos/go-oidc/v3`, a thin layer over the existing `golang.org/x/oauth2`) registers its own `infra/login.RedirectProvider` — Keycloak, Authentik, ADFS, Entra, or any spec-compliant issuer — so `GET /api/login/{key}`/`GET /api/callback/{key}` work exactly like Google/GitHub. `NewOidcLogin` runs OIDC discovery (`{issuer}/.well-known/openid-configuration`, 10s timeout, optional pinned CA via `ca_cert_path` for a private-CA intranet IdP) at startup; a bad/unreachable issuer or missing `client_id`/`client_secret` logs a warning and skips just that provider, same fail-soft policy as Google/GitHub/Kerberos. The login leg runs PKCE (S256) plus a nonce, both riding single-use HttpOnly cookies scoped to the callback path; the callback verifies the `id_token` against the discovered JWKS, checks the nonce, and rejects an explicit `email_verified=false` unless the per-provider `insecure_skip_email_verified` override is set (an absent claim is accepted); that rejection now names the address (`identity provider reports the account email as unverified: <email>`) since it becomes the audit record's detail. Accounts bind to `oidc:<key>` (`Identity.Provider`) — changing an entry's `key` orphans existing federated accounts, so it is treated as a stable identifier, not a display label. The client secret can also come from `OIDC_<KEY>_CLIENT_SECRET` (`infra/apphost/run.go`). A configured `groups_claim` feeds `apps/myidsan/services.IDirectoryService.AdmitExternalIdentity`, which seeds a role from a `FederatedGroupMapping` scoped to `oidc:<key>` for a still-pending account only — always non-authoritative, unlike LDAP's optional re-apply-every-login mode, because an external IdP's groups claim is only as fresh as the last login. **The bench found and fixed a real gap**: `providerCallback` had audited only successful federated sign-ins, so every refused SSO attempt (a tampered `state`, a callback with no flow cookies, an unverified email) was invisible on the audit page while a refused password login was recorded. All four federated rejection paths now call `recordFederatedLoginFailure` (`apps/myidsan/apis/login.go`), recording `login.failure` with `{method, provider}` metadata — and deliberately do **not** advance the `LoginGuard` failed-login lockout, since the credential was checked at the IdP, not guessed against myidsan. See `docs/HOWTO.md`'s OIDC setup subsection (Keycloak example) for IdP-side configuration.
- **TOTP two-factor authentication** (`docs/MYIDSAN_MFA_PLAN.md`, shipped): self-service RFC 6238 TOTP enrollment (`POST /api/mfa/enroll` → QR + base32 secret, `POST /api/mfa/enroll/verify` → confirms and mints 10 single-use bcrypt-hashed recovery codes shown once) plus status/regenerate/disable, all on the self-service **Profile** page (`GET/DELETE /api/mfa`, `POST /api/mfa/recovery`) and gated only on the caller's own account. Both **local** (`/api/login/default`) and **LDAP** (`/api/login/ldap`) password logins are gated unconditionally once a factor is confirmed — the credential check succeeds but, instead of a session cookie, the response is `{mfaRequired:true, mfaToken}`; the session is only issued after `POST /api/login/mfa` (SPA) or `POST /api/auth/mfa` (the server-rendered federated login page) redeems the token + a TOTP or recovery code. `mfaToken` is opaque, single-use, cache-backed (`infra/mfa` primitives + a new `mfaChallenger` in `apps/myidsan/apis`), 5-minute TTL, capped at 5 attempts, and bound to a client IP+User-Agent fingerprint so it cannot be redeemed from a different client. Kerberos SPNEGO and OIDC/Google/GitHub logins are **not** gated — the upstream IdP owns factor policy. The shared secret is sealed at rest the same way the LDAP bind password is (`infra/atrest`). Superadmin can clear another user's factor at `DELETE /api/mfa-admin/{id}`; a `RESET_MFA` marker file in the data dir (mirroring `RESET_ADMIN`) recovers the stock superadmin's own MFA lockout without touching its password. New metric `myidsan_mfa_challenge_total{result}`. **MFA enforcement policy** (Productization Phase 3, config block `mfa`) now exists: `mfa.policy` is `off` | `optional` (default) | `required`; under `required`, `mfa.requiredRoleIds` optionally narrows the requirement to specific roles (empty means every role), and `mfa.applyToDirectory` (default `false`) decides whether LDAP-bound accounts are in scope. Enforcement is checked **after** a successful password login, at the same layer as the forced-password-change gate (`AccessPrincipal.MustEnrollMfa`, `middlewares.MfaEnrollmentRequiredCode`) — the account gets a session but is pinned to the enrollment screen, never refused outright, since refusing the login would lock out every existing administrator the instant the policy is switched on.
- **Account recovery ("forgot password")**: a public, non-committal `POST /api/login/forgot` (SPA) / `POST /api/auth/forgot` (server-rendered), rate-limited via the shared `LoginGuard`, always returns the same generic response regardless of whether the submitted identifier matched an account — no account-enumeration oracle. Two channels: an always-on **operator queue** (`apps/myidsan/entities/password_reset_request.go`, `apps/myidsan/services/password_reset.go`) — superadmin-only `GET /api/password-reset` lists pending requests, `POST /api/password-reset/{id}/resolve` force-sets and returns a one-time temporary password (`IUserLoginService.AdminResetPassword`, must-change flagged), `POST /api/password-reset/{id}/dismiss` closes a bogus one — and an **optional** self-service email link via a new pure-stdlib `infra/mailer` SMTP sender, gated by a new `smtp` config block (`enabled` default `false`, `host`/`port`/`from`/`username`/`password`/`useStartTls`; refuses to authenticate over a non-STARTTLS connection). When mail is enabled, a single-use, 30-minute, cache-backed token (`GET/POST /api/auth/reset?token=...`) lets the user set their own password (`IUserLoginService.SetPasswordSelfService`) — deliberately does **not** issue a session, so any enrolled MFA factor is still presented at the next normal login. Only **local** accounts are eligible; LDAP/Kerberos/OIDC accounts are excluded (directed to their upstream IdP). An air-gapped install leaves `smtp.enabled` false and the operator queue is the sole recovery channel, with zero network egress.
- **Self-service Profile page + profile pictures**: change-password, TOTP MFA management, and a new profile-picture (avatar) editor are consolidated into one self-service **Profile** page, reached only from the account chip in the side rail (`chipOnly` route, not a nav item or dashboard tile — `routeCatalog`'s `profile` entry, `apps/myidsan/views/react-webpack/src/views/App.js`). It is the first in-app self-service change-password form for myidsan (`POST /api/login/default/change-password`, previously only reachable via the forced first-login `ChangePasswordScreen`). Profile pictures are backed by a new `UserAvatar` entity (`apps/myidsan/entities/user_avatar.go`, one base64-JPEG row per account in a `TEXT` column, `json:"-"`, never carried in JWT claims) and `apps/myidsan/apis/profile.go`'s `profileApi`: self-service `GET/POST/DELETE /api/profile/avatar` (auth-only, own account) plus a superadmin `GET/POST/DELETE /api/profile/avatar/{userId}` surface that lets an operator set any user's picture inline from the **Users** page (`RowAvatar`'s camera button). The client center-crops and resizes to a 256px JPEG (`<canvas>`, `resizeImageToDataUrl`) before upload, so the server needs no image codec — only a MIME allow-list (`image/jpeg`/`png`/`webp`/`gif`) and a 512 KB decoded-size cap; a missing avatar is a plain `404` the SPA renders as an initials fallback, not an error. See `apps/myidsan/apis/profile.go.md` and `apps/myidsan/entities/user_avatar.go.md`.
- **Backup & restore** (`docs/MYIDSAN_PRODUCTIZATION_PLAN.md` Phase 1, shipped): superadmin-only, not delegatable through the RBAC matrix (`apps/myidsan/apis/backup.go`, `apps/myidsan/services/backup.go`) — `GET /api/backup/sections` (row counts per section), `POST /api/backup/export` (passphrase ≥ 12 chars required), `POST /api/backup/preview` (decrypts only the manifest), `POST /api/backup/restore`. Produces/consumes a single `.idbackup` file (magic `IDBK` + format version, then an `atrest.EncryptWithPassphrase`-sealed JSON payload) covering six ordered sections — access (roles/permissions), identity (users/groups/avatars), MFA (TOTP factors/recovery codes), apps (app registry/auth config/redirect URIs), federation (directory config/group mappings), and the SSO CA. The two at-rest-sealed values (TOTP secrets, the LDAP bind password) are **unsealed on export and re-sealed with the destination host's own at-rest key on restore** — the at-rest key itself never travels, which is what lets a backup restore onto a brand-new host and still pass a TOTP check. Restore remaps every foreign key onto freshly-created destination ids (`replace` mode wipes each selected section's tables first; `merge` appends) and **skips** any row whose parent id is not present in the backup rather than leaving a dangling/ambiguous grant (e.g. a permission whose role wasn't restored, a redirect URI whose auth config wasn't restored) — reported back per-section as `Skipped` counts. A restore always drops every live session (`cache.Store.DeleteByPrefix("sso:session:")`, since a session token now refers to ids/roles that may mean something different) and marks first-run setup complete. Reachable from **Backup & restore** in the nav and from the first-run wizard's "restore from a backup instead" path. See `apps/myidsan/README.md` and `deploy/README-myidsan.md`'s DR runbook.
- **Audit log, session administration, and step-up re-authentication** (`docs/MYIDSAN_PRODUCTIZATION_PLAN.md` Phase 2, shipped): an append-only `AuditLog` entity/service (`apps/myidsan/entities/audit_log.go`, `apps/myidsan/services/audit.go`) records login success/failure/lockout/logout (with the sign-in method — local/ldap/kerberos/oidc/social/recovery_code), MFA enroll/disable/admin-reset/recovery-use, user create/update/delete, directory config updates, password-reset resolution, backup export/restore, session revocation, and step-up success/failure — write-only from inside the product; there is no update route and no way to delete a chosen row. **The one exception is age-based retention** (`config.audit.retention`, off by default; `infra/config/audit_retention.go`, `apps/myidsan/services/audit_retention.go`): a periodic scheduler task (`apps/myidsan/app/audit_retention.go`'s `startAuditRetention`, gated on `enabled`) archives every row past `maxRetentionDays` (default 365, floor 30 — anything configured lower is raised with a startup warning) to a JSON-lines file under `archiveDir` (default `audit-archive`), fsyncs and renames it into place, and **only then** deletes those rows — a run that cannot finish its archive deletes nothing. The purge records itself back into the trail (`audit.retention_purge`) naming the cutoff, row count, and archive file, so a reader who finds history starting abruptly can tell a deliberate trim from an empty past. A failed sign-in is recorded with `ActorId 0` and the ATTEMPTED identifier as `ActorEmail`, since the caller has no identity yet; `UserAgent` is captured on every event, which myseliasan's equivalent audit log does not carry. Superadmin-only `GET /api/audit` (filter by action/outcome/actor/target/date range) and `GET /api/audit/export.csv` (`apps/myidsan/apis/audit.go`) share one filter-parsing helper so an export always matches what the screen showed; `csvSafe()` prefixes a leading `=`/`+`/`-`/`@`/tab/CR with a quote to defuse spreadsheet formula injection, since the export carries attacker-influenced text (a failed-login username, a User-Agent). Client addresses recorded anywhere in the trail are resolved by a newly-exported `domain/utils/middlewares.ClientIP`/`ParseTrustedProxies` (factored out of the rate limiter's previously-private copy) so the audit trail and the rate limiter cannot disagree on which peers may declare a forwarded address — unlike myseliasan's audit log, which trusts `X-Forwarded-For` unconditionally. The long-declared-but-never-written `user_session` table (`domain/entities/user_session.go`) is now populated on every session issued (gained `IpAddress`/`UserAgent`/`LastSeenAt`) by a new `ISessionService` (`apps/myidsan/services/session.go`): the cache entry at `sso:session:<sid>` remains the authority the auth middleware checks, this table is only an INDEX so sessions can be listed per user, and a revoke deletes the cache entry first so a bookkeeping failure never leaves a live session claiming to be dead. `GET/DELETE /api/session`, `POST /api/session/revoke-all` are auth-only self-service (reviewing/ending your own sessions is deliberately not RBAC-matrix-gated, the same reasoning as `/api/mfa`); `GET/POST /api/session-admin/user/{id}[/revoke]` are superadmin. Disabling or deleting an account now ends its sessions too (`apps/myidsan/apis/user_login.go`'s `endSessionsFor`) — previously a disabled account's already-issued session kept validating against the auth-only surfaces (`/api/profile/*`, `/api/mfa`) for up to the full 72-hour token lifetime, since the cached session entry carries no account-status flag. A new `IStepUpService` (`apps/myidsan/services/stepup.go`) is a 5-minute, cache-backed, session-id-keyed re-authentication marker (password, plus TOTP when a factor is enrolled) gating `POST /api/backup/export`, `POST /api/backup/restore`, `DELETE /api/mfa-admin/{id}`, and `POST /api/password-reset/{id}/resolve` — the four actions a stolen 72-hour superadmin cookie could otherwise use to export/replace the whole identity store, strip someone else's second factor, or hand out a working credential, with no further proof of identity. `GET/POST /api/step-up` (auth-only) reports/grants elevation; a failure records `stepup.failure`, since it is what an attacker holding only the cookie produces while trying to escalate.
- Local credential passwords are stored as bcrypt hashes, with lazy migration from legacy plain-text values on successful login.
- Authorization: shared "accessrbac" RBAC core — single-app, no `app_code` dimension. Each app (myidsan, myseliasan) has its own `access_role` and `access_role_permission` tables in its own database. Built-in roles `superadmin` (matrix bypass) and `viewer` (no default permissions) are seeded on startup. The legacy `GET /api` read-everything wildcard previously seeded for viewer is **stripped** on startup by `EnsureViewerDefaults`; viewer now starts with no permissions. The permission matrix is a prefix-match table: each row grants a role access to an endpoint path prefix per HTTP verb; longest prefix wins; no match = deny. Menu visibility in both SPAs is derived from the same matrix via `GET /api/access-rbac/me` (auth-only; superadmin gets `isSuperadmin: true` / wildcard; others get their permission rows; `pending: true` when no role is assigned). Role is **dynamic**: `AccessSessionMidware` re-stamps `claims.RoleId` from the live user store on every request so a role change takes effect immediately without a re-login, and the session role-mismatch check is removed from `validateSession`. `IsSuperadmin` also resolves live. A new `RequireSuperadmin` middleware locks a subrouter to superadmins regardless of matrix grants; it is applied to `/api/user-credential`, `/api/user-group`, and `/api/rbac/users` in myidsan/myseliasan. `ListForRole` (permissions + node grants) sorts by path ASC for stable RBAC matrix UI updates. All shared admin APIs and app-local admin APIs are enforced by `AccessSessionMidware`. **Critical bug fix**: `SelectByUnique` in both the SQLite and PostgreSQL adapters now fails closed when the key group matches no struct field — previously it issued an unfiltered `LIMIT 1` query, silently returning the first row. Five callers that used `GetByUnique(ctx,"","id",id)` (matching no field) have been switched to `GetById` (primary key); `genericRepo.GetById` and `GetByUnique` now also return `(nil, nil)` when the underlying query returns a nil map, so every `x == nil` not-found check in auth/RBAC is correct. A regression test was added to `db_crud_test.go`.
- `myidsan` is the SSO identity provider for cross-app browser login. Tokens carry issuer (`iss`), audience (`aud`), expiry, session id (`sid`), resource app code, and policy version. Redis should be used for shared session cache in multi-process deployments. `myidsan` no longer issues RBAC decisions to relying apps; each app enforces its own accessrbac matrix locally.
- `mymatasan` is a standalone device app and does not mount MyIDSan login, SSO browser callback, user/group, accessrbac, app-registry, endpoint-RBAC, file-storage, log, runtime-log, or cache-service management APIs. App-local ONVIF and vision routes use DB-backed local Basic Auth (with a session cookie for media elements). Saved-camera browser live view uses configurable RTSP-to-WebRTC H264 forwarding first, with MJPEG fallback retained for compatibility. If the key is missing but a marker shows one existed, the app boots into a public pre-login **recovery gate** (`GET/POST /api/system/recovery/gate`, `/unlock`) where the escrow file + passphrase restore access, or restores automatically with no prompt when `security.recoveryPath` + a passphrase are configured. Distinct from that key escrow, the same tab's **Configuration backup** panel exports/imports a portable, passphrase-encrypted `.mmbackup` bundle (`GET /api/settings/backup/sections`; `POST /api/settings/backup/export`/`preview`/`restore`) covering the camera, AI-detection, notification, and app-settings rows — including the plaintext secrets (camera/ONVIF credentials, notification tokens) the normal API strips — via a portable Argon2id+AES-256-GCM primitive (`infra/atrest.EncryptWithPassphrase`/`DecryptWithPassphrase`) that is **not** tied to the machine's at-rest key, so a file made on one host restores on another; restore reassigns primary keys and remaps foreign keys (cameras first, building an old→new id map) and the first-run wizard's welcome step offers the same restore for a fresh install. A **Secure Wipe & Reset** (factory reset: crypto-erase key → erase media → drop/rebuild DB → TRIM + free-space scrub → restart) is available only when `bootstrap.allowReset` is enabled. `mymatasan` also accepts tunneled commands from the `myseliasan` control plane over the control channel (parent→node reverse tunnel); these are re-injected into the node's own API router with a synthetic principal whose role is resolved from the parent's asserted role NAME against the node's OWN roles, so the node's own permission matrix — not the parent's — decides what the command may do (the node owns the data, so the node's policy must govern; `"admin"` stays accepted as a wire alias for `superadmin` for a mixed-version fleet).
- **Cross-domain fleet rules (correlation)**: once `myseliasan` has adopted both camera and IoT nodes, it can express rules no single node can evaluate alone — e.g. motion on a camera node AND a door contact opening on an IoT node AND no badge swipe → intrusion. `services.Correlator` (`apps/myseliasan/services/correlate.go`) evaluates `FleetRule`/`FleetRuleClause` (each clause: `"required"` or `"absent"`, optionally scoped by node id, node kind, notification category, and/or a text match) against the same node events already flowing into the unified feed — fed the raw event a node pushed up the control channel, never the control plane's own re-published copy of it (mixing the two would let one rule's alert satisfy another rule's clause and let two rules trigger each other forever). A rule never fires on an event: when its required clauses are all satisfied within `WindowSeconds` it **arms**, waits out `GraceSeconds`, and only then (on a 1-second sweep ticker) checks whether the absent clauses still hold — an absence you have not waited for is not an absence, it is a race with a slow badge reader, and firing without the wait would cry intrusion on every legitimate entry. A rule made only of absent clauses is refused at save time and again at evaluation time, since it would fire on nothing at all forever. Writing/deleting a rule (`POST`/`DELETE /api/fleet-rules`) is superadmin-only; reading (`GET /api/fleet-rules`) is open to any authenticated session. A clause's node-kind scope is resolved from the adopted node's own `ManagedNode.Kind` record, never from anything the event body claims.
- `myseliasan` is a relying control-plane app and has no public landing page. It redirects unauthenticated users to MyIDSan and creates its own local session only after MyIDSan returns a valid authorization code. It maintains its own `ControlUser` store (local stock superadmin + federated myidsan users), with roles governed by the shared accessrbac core. It communicates with `mymatasan` nodes over LAN using the pairing protocol (see below) and the reverse command tunnel (see below); it does not relay through `myidsan` for either pairing or authorization.
- **The node-side fleet stack is shared, not per-app**: LAN discovery, adoption, mTLS enrollment, the control channel, and the event sink (`domain/shared/fleetnode`, moved there from `apps/mymatasan/services` when `myiotsan` needed the identical stack — a second copy would be a second copy of a security protocol, and the two would drift the first time one was fixed; `mymatasan`'s own call sites are unchanged via same-named aliases in `apps/mymatasan/services/fleetnode.go`). **A node now has a `Kind`** (`"camera"` for `mymatasan`, `"iot"` for `myiotsan`) that travels two different ways on purpose: the discovery announce carries it as an **advisory, unsigned** hint (`infra/pairing.Announce.Kind` — deliberately excluded from the HMAC, because signing it would break every already-deployed `mymatasan` node the moment a control plane upgraded), while the adopt call returns it **authoritatively** (`fleetnode.AdoptResult.Kind`, itself fleet-key-signed and claim-code-gated) — and that is the value `myseliasan` stores on `ManagedNode.Kind`. A hostile host on the LAN can make a fake node show the wrong icon in a scan list; it cannot make the control plane adopt anything or change what an already-adopted node is. An empty/unset `Kind` means camera, since every node adopted before the field existed is one.
- **LAN discovery + single-parent adoption + mTLS hardening (pairing protocol)**: `mymatasan` nodes and the `myseliasan` control plane share a fleet key (PSK, operator-set). Discovery uses authenticated UDP multicast (HMAC-SHA256 signed probes + announces, nonce + timestamp replay protection). A node is discoverable only when it is unpaired and a fleet key is set; it goes silent once adopted. Adoption is an HTTPS call carrying a fleet-key assertion (proves key possession without transmitting it) and a short-lived operator-generated claim code; the node issues a single-use pairing token and stores only its hash. The control plane stores the token for later enrollment calls. After adoption the node immediately generates an ECDSA P-256 key + CSR locally (the private key never leaves the node) and POSTs the CSR to the control plane's `POST /api/nodes/enroll`, which is authenticated by the pairing token; the control plane's on-prem fleet CA (ECDSA P-256, 10-year self-signed root, persisted in `ControlSetting`) signs the CSR, setting the CN to the node ID authoritatively (ignoring the CSR subject). The node parses `result.nodeCert` from the enrollment response (with `data.result.nodeCert` as a legacy fallback) — prior to this fix, the cert was silently empty on the standard envelope and the control channel never connected. The node stores the issued cert + CA root (AES-256-GCM encrypted at rest); the control plane records `CertExpiresAt`. Ongoing management runs over mutual TLS: the node serves a dedicated mTLS management listener (config field `pairing.mtlsPort`; code fallback 49532 when unset, but the shipped `config.json` now sets 39532 — moved off the 4953x range to avoid a Windows port conflict) presenting its node cert, requiring a client cert signed by the fleet CA. The control plane probes it periodically (`GET /heartbeat`, configurable interval via `pairing.heartbeatIntervalSeconds`, default 60 s) as a **fallback** liveness mechanism — the authoritative signal is whether the node holds a live control-channel connection (`ControlServer.IsConnected`); the mTLS poll can no longer flap a control-connected node offline. Only nodes without a live control connection are mTLS-probed at all, and that probing now runs concurrently through a bounded worker pool (`heartbeatProbeConcurrency` = 16) under a per-sweep budget (`heartbeatSweepBudget` = 30 s) rather than serially, so a batch of unreachable nodes can no longer stall the whole sweep past the heartbeat interval; DB reconciliation/writes stay serial (single-writer sqlite). A node is declared `lost` only after a grace window (3× heartbeat interval, floor 90 s) with no contact on either path. `NodeRegistry.List` likewise now pages through the store (500 rows/page) instead of a single hardcoded 1000-row `Get`, so the operator Nodes list, `Scan` adoption dedup, and this heartbeat sweep all see the whole fleet regardless of size. Release over mTLS (`POST /release`) is preferred over the token leg; on `Release`, the control plane first revokes the node's cert (refuses future renewals) then deletes its registry row. Nodes attempt to renew certs automatically via the same CSR flow before `pairing.renewBeforeHours` (default 48h) of expiry, but **that renewal is now gated per node**: `ManagedNode.AutoRenew` (default `false` for a newly adopted node) must be turned on by an operator (`PUT /api/nodes/{id}/auto-renew`) before the control plane's `Enroll` will honour a renewal (`ErrRenewNotAuthorized` otherwise) — the very first enrollment right after adoption is never gated, and the renewal itself still needs no claim code, only the node's existing pairing token. A node nobody blesses lets its cert lapse on its own default 90-day TTL (`pairing.certTtlHours`, raised from 7 days for this reason) and drops out of the fleet — a per-node dead-man's switch. A one-time startup backfill (`INodeRegistry.BackfillAutoRenew`) turns auto-renew on for every node already enrolled before this feature shipped, so an upgrade does not surprise-expire an existing fleet. Revocation (deliberate, operator-initiated) remains "refuse to renew + short TTL" — no CRL/OCSP — and is now joined by this quieter, default-on renewal gate as the second way a node's trust lapses. Identity in the mTLS channel is carried in the cert CN (SAN-free); both sides verify CA chain + CN rather than hostname, because appliances are dialed by IP. Both node admin self-drop and control-plane release are supported; a best-effort fleet-key-signed notice keeps the registry consistent on self-drop. The `ManagedNode.Fingerprint` field is reserved but not used; identity verification uses CN, not a pinned fingerprint. In addition to the periodic heartbeat channel, the node dials a persistent bi-directional control channel to the parent's `pairing.controlPort` (code fallback 49533; shipped `config.json` sets 39533) over fleet-CA mTLS; this channel carries parent→node tunneled commands and node→parent event pushes (notifications, going-offline). A second dedicated media channel (`pairing.mediaPort`, code fallback 49534; shipped `config.json` sets 39534) carries binary camera RTP frames for node-camera live view relay (see below). **Adopt-persist rollback**: a node commits `Paired=true` and burns its single-use claim code the moment it replies to the parent's adopt call, so if the control plane then fails to save the `ManagedNode` row (a DB hiccup, a schema mismatch), the node was previously left permanently stranded — paired but recordless, invisible to discovery, unable to retry with the now-spent claim code. `NodeRegistry.Adopt` now best-effort releases the node's own pairing (`POST /api/pairing/release` with the token it just returned) before surfacing `ErrAdoptPersist`, so it becomes discoverable and adoptable again; the API layer logs the raw DB error server-side and returns an actionable client message rather than the raw string. **Stranded-node visibility**: separately, a node that already holds a valid enrolled cert but has no managed record (released here without being reset there, or a lost row) keeps dialing the control channel and being refused — previously invisible beyond a log line. `ControlServer` now tracks each refusal (deduped by node id, bounded at 200 entries, evicting the stalest) and exposes it via `GET /api/nodes/unrecognized`; an operator can `POST /api/nodes/{id}/block` (revokes the cert via `NodeRegistry.RevokeNode`, which needs no managed row) or `POST /api/nodes/{id}/forget` (dismiss without revoking). `AcceptControlConn` checks revocation **before** the row lookup, so a blocked-but-row-less node correctly reports "revoked" rather than a generic "unknown node" that would make the Block action look like it did nothing.
- **Fleet secret encryption at rest (myseliasan control plane)**: the fleet CA private key (`pairing.caKey`), the control plane's own parent leaf private key (`pairing.parentKey`), and the fleet PSK (`pairing.fleetKey`) previously sat in plaintext `ControlSetting` rows. `apps/myseliasan/services/secret_store.go` now wraps them with the same reusable `infra/atrest` AES-256-GCM module mymatasan uses for media (`base64(atrest ciphertext)` in the TEXT column), resolved from the same shared `security` config block (`encryptAtRest` default true; `keyPath` default `<dataDir>/secret/atrest.key`, myseliasan's own key independent of mymatasan's). Public certs and the revocation list stay plaintext. Legacy plaintext rows are read transparently (no migration). Unlike mymatasan's public recovery gate, a missing-but-previously-existing key here **fails closed**: `app.go`'s `openFleetSecretCipher` refuses to boot rather than mint a replacement key and silently reset the whole fleet's trust.
- **Node camera WebRTC media relay**: the node dials the parent's `pairing.mediaPort` (39534 in the shipped config; 49534 code fallback) with a dedicated `MediaChannelManager`. On a browser `POST /api/nodes/{id}/cameras/{cam}/webrtc/offer`, myseliasan's `MediaRelayHub` asks the node to stream the camera RTP, waits for codec metadata (`FrameMeta`), then creates a WebRTC peer (`stream.Manager` via `relayConnector`) with the same H264+audio track path used for local cameras. A shared `stream.WebRTCEngine` (from `nodeStream.publicIps`/`nodeStream.udpPort`) advertises the parent's external IP and binds a fixed UDP port for cross-network browser connections. STUN/TURN (`nodeStream.iceServers`) is offered to the browser for the parent↔browser leg. `GET /api/node-stream/config` returns the current ICE server list. For same-LAN deployments no `nodeStream` config is needed. The `ParentBaseURL` the node dials for control and media channels defaults to `sso.redirectBaseUrl` but is overridden by `pairing.parentBaseUrl` in config when node and parent are on separate machines.
- **Embedded node camera pages (myseliasan control plane)**: selecting a camera in the side-nav node tree opens that camera's actual `mymatasan` page — Live View / Detection / Recordings / Settings tabs — inside myseliasan, driven entirely over the control/media channels (the browser never talks to the node directly). The tab components (`node_detection.js`, `node_settings.js`, `node_recordings.js`, plus `NodeLiveView`/`NodeCameraTile` in `node_manager.js`) are thin routing wrappers around the **real mymatasan source files** copied into `apps/myseliasan/views/react-webpack/src/views/components/nodecam/` (`vision.js`, `recording.js`, `previews.js`, `cameras.js` pieces, `ui.js`, `layout.js`, `hooks.js`, `ptz.js`, helpers/constants), so behavior stays byte-for-byte identical to the node's own UI. Two shims make the copied code work unmodified against a remote node: `nodecam/lib/helpers.js`'s `apiBase()` is repointed at the commander proxy (`/api/nodes/{id}/proxy`) instead of same-origin, and `installProxyCsrf` teaches `window.fetch` to attach myseliasan's CSRF token on proxy writes. Design parity is achieved without a build-time CSS fork: `webpack.config.js` adds a `@mymatasan` alias to the mymatasan app's view source and a `?raw` CSS rule, `nodecam/mymatasan_css.js` imports mymatasan's real stylesheets as strings, and `nodecam/scoped_css.js` injects them once and rewrites the CSSOM to prefix every selector under `.nodecam-embed` (`NodeEmbed` in `node_embed.js`) — so mymatasan design changes flow through automatically on the next myseliasan build, with no manual re-sync and no Shadow DOM (keeping normal React event/input behavior). A cross-node **Live Views** wall (`components/live_views.js`, `lib/live_views_store.js`, localStorage-backed) lets an operator pin cameras from any node into one grid, and a **Node Dashboard** (`node_dashboard.js`) mirrors mymatasan's own analytics dashboard over the tunnel. Each embedded section shows a `NodeFeatureBanner` instead of a silent blank when the node's endpoint 404s (an older node that predates the feature), rather than failing silently. Recorded video playback needs its own range-capable path — see the reverse command tunnel entry below and `apps/myseliasan/apis/recording_stream.go.md`.
- **Fleet Map / GIS (myseliasan control plane)**: an offline geographic + indoor spatial view of the fleet, scoped entirely to `myseliasan` (not core). It is a **digital twin built on sites, not appliances**: a `Site` carries its own `Lat`/`Lon`/`MapPlaced`/`Icon`/`Kind` (mirroring `ManagedNode`'s `Lat`/`Lon`/`MapPlaced`) and is what the geographic view anchors cameras to, since a node's own box may sit in a rack, another site, or off-site while its cameras are placed on that site's floor plans regardless. `Site.Kind` (`entities.SiteKind*`/`NormalizeSiteKind`) is one of `building` (has storeys, drawn/stacked in 3D), `outdoor` (one open ground surface — a park, yard, campus — exactly one plan, no "how many areas" step) or `point` (a junction/pole/gate with **no plan at all**; its cameras reach it only through the node(s) assigned via `SiteId`); an empty/unrecognised kind normalises to `building` so every pre-existing site keeps its old meaning. The geo view draws exactly one marker per site, shaped by kind (disc/square/diamond — `markerShape` in `fleet_map.js`) so the silhouette still reads a site's kind when zoomed past the name label (`GET /api/sites/overview`, a per-site rollup of owning-node health + camera/floor counts). A node appliance never draws its own pin — there is no standalone/off-site node placement any more (the old "place on map" action, node drag-to-place, and the Nodes-layer toggle are gone from the frontend; the node-pin map layer still exists in code but is fed no data). Clicking a building/outdoor marker opens its floor-plan drill-down as before; clicking a point marker instead opens the device card of the node(s) assigned to it (a chooser when several, an empty state when none), since there is no plan to drill into. `ManagedNode.SiteId` (`PUT /api/nodes/{id}/building`) assigns/clears the building an appliance *resides in*, via a building-selector dropdown on the rail's "Appliances" section (nodes not yet assigned to any building) rather than a drag-onto-map gesture; a node with no `SiteId` is simply not represented on the map until assigned. `ManagedNode.Lat`/`Lon`/`MapPlaced` and `PUT /api/nodes/{id}/position` still exist at the API layer (`MapPlaced` distinguishes "deliberately positioned" from the zero value, since `(0,0)` is itself a real coordinate) but are no longer driven by any reachable UI action. A site marker's unread-notification badge is attributed **per camera** (`GET /api/notifications/tally`, `domain/notification.Service.Tally`), not per whole owning node, since one node can record cameras across several sites. Clicking a building or outdoor marker opens `BuildingFloorView` — every floor of that site with **every** camera on it regardless of owning node (`GET /api/sites/{id}/floorplans`, `services.SiteFloorplans`), each marker/wedge coloured and streamed by its own owning node — versus `NodeFloorView`/`GET /api/node-floorplan/{nodeId}` which is scoped to one node's own placements. The basemap is one or more self-hosted [Protomaps](https://protomaps.com/) `.pmtiles` **region** archives (a fleet spanning disjoint areas is several region files, not one planet-sized archive) served by `apps/myseliasan/apis/basemap.go` (`GET /api/basemap/info` lists regions + bounds, `GET /api/basemap/tiles/{name}` — Range-served via `http.ServeContent`, deliberately never behind a compression middleware since a region's tiles are already gzip-compressed internally and addressed by absolute byte offset a re-compressing layer would corrupt). An empty/absent basemap directory is a supported state (`available: false`) — the map still renders markers without cartography rather than requiring a ~200MB asset to boot. When an operator (or `MYSELIASAN_BASEMAP_SOURCE`/`MYSELIASAN_PMTILES_BIN`) configures a remote pmtiles source and the `pmtiles` tool is present, `POST /api/basemap/download` extracts a new bounded region on demand (bbox ≤25°×25°, zoom ≤14) — the one action in this otherwise air-gapped app that deliberately reaches the internet, off by default. The indoor view (`apps/myseliasan/apis/sites.go`, `services/sites.go`) is authored entirely from the geographic map, not a separate tab: a `+ Add` rail button opens `asset_wizard.js` (replacing the old building-only `building_wizard.js`), whose first question is the site's kind — building/outdoor/point — since that decides everything after: a per-kind glyph palette, and (building only) whether it is a single area or several (each area becomes a `FloorPlan` row; outdoor gets exactly one, point gets none); on save the site + areas are created (`POST /api/sites` now taking `kind`) and, for a building/outdoor site, the map enters placing mode so the operator drops the marker, which opens `building_editor_dialog.js` — a near-fullscreen modal with area tabs, a node/camera palette, and the `FloorEditor` canvas (`floor_editor.js`) for drawing; a point site has no plan surface, so dropping its marker simply places it. The side rail itself is site-centric, grouped by kind: every site (placed or not) is listed with a status dot and camera count; a building/outdoor row is expandable (lazily fetching `GET /api/sites/{id}/floors`) to that site's floors/areas — clicking a floor row opens the drill-down on that specific area — while a point row's pencil opens a small rename/re-glyph dialog directly, since it has no editor. An area's plan image starts as either an **uploaded** image (`POST /api/sites/{id}/floors`, PNG/JPEG/GIF ≤24MiB) or a **generated blank canvas** (`POST /api/sites/{id}/areas`, `services.AddBlankFloor` — a white PNG rendered server-side, default 1600×1000, capped at 8000px/side, so the wizard/editor never has to rasterise and upload a blank image client-side); either way the operator then draws walls/rooms over it in the same in-app editor, whose toolset follows the site's kind (building: Select/Wall/Room/Round/Door/Window/Stairs/Platform/Erase; outdoor: Wall/Room/Round/Gate/Parking/Platform/Erase), plus grid-snap, undo/redo, a multi-select transform gizmo (move/resize/rotate, oriented to a single selected object's own rotation), copy/cut/paste (geometry only — a camera marker is placed exactly once fleet-wide and cannot be copied), on-canvas camera POV drag handles, pan/zoom, and a draggable/dockable tool palette and properties inspector, whose vector shapes round-trip through `FloorPlan.Design` so a drawn plan can be reopened and re-edited, not just flattened to an image; an uploaded photo can likewise be annotated later, at which point its pristine original is preserved as `FloorPlan.BgPath` (`GET /api/floors/{id}/background`) so re-editing never draws over an already-composited render (`POST /api/floors/{id}/image` replaces the rendered image + design on save, also how a blank area's canvas is swapped for a real scan/CAD export; `DELETE /api/floors/{id}/image`, `services.ClearFloorImage`, is the inverse — it clears the picture back to that same blank canvas while leaving the drawn walls/stairs/doors and every camera placement untouched, for an operator who wants the authoring but not the photo). The same editor has a **2D ⇄ 3D** toggle: the operator's painted wall/room layout plus a real-world `Scale` (metres/pixel), `WallHeight` and per-floor `Elevation` (`FloorPlan.Grid`/`Scale`/`WallHeight`/`Elevation`, autosaved debounced via `PUT /api/floors/{id}/model`) are extruded into a three.js scene (`floor_3d.js`, code-split, loaded only when 3D is opened), with floors stackable by `Elevation` for a multi-floor building. The 3D view extrudes **exactly** the walls present in `Grid.segments` — a floor with none renders as a bare slab, not a fallback perimeter box, since an outer wall is authored by the operator rather than invented by the viewer. `Grid` also carries `stairs[]` (straight-flight footprints with a chosen step count, their own climb height, a rotatable ascent direction, an up/down toggle, and — when dropped on a `platforms[]` entry — a lock onto it as the flight's base, extruded as rising steps to storey height; a down flight carves a stairwell opening into the floor slab above), `doors[]` (openings that carve a gap in a wall segment in both the 2D canvas and the 3D extrusion, hinge/swing mirrorable for the four real door hands, with a lintel left above each opening), `windows[]` (a glazing opening with no swing), `platforms[]` (a raised floor with an adjustable rise, rendered as a carved slab in 3D), and `parking[]` (striped bays, outdoor only) alongside the wall `segments[]`. The read-only 2D drill-down (`node_floor_view.js`'s `FloorPlanGrid`) now renders this same authored geometry as a vector overlay too, not just the 3D tab. A camera placement with unread notifications (see the per-camera `notifications/tally` attribution above) renders a severity-coloured count badge in both the 2D plan (`node_floor_view.js`) and the 3D view (`floor_3d.js`, a billboard sprite drawn depth-test-off so it reads through walls); the 3D view additionally animates a two-wave pulse on the floor beneath the camera, the same beacon treatment as the geographic view's building marker — visible on every stacked floor but animated only on the active/non-dimmed one, and recomputed into the scene's rebuild signature so a new alert appears immediately. Nodes/cameras are dragged onto a plan as `NodePlacement` rows keyed to a pixel position in the image (the image's own `Width`/`Height`, captured at upload/creation, become the OpenLayers pixel-projection extent). **Placement is exclusive**: `(NodeId, CameraId)` is a DB unique index (`ux_node_placement_camera`), and `services.AddPlacement` checks it first via `FindPlacementOf`, refusing a second placement with `*ErrAlreadyPlaced` (mapped to `409` by `apis/sites.go`, naming the site/floor the camera already sits on) — a camera holds at most one pin fleet-wide; moving it means unplacing it first. `GET /api/placements` (`services.PlacementIndex`) lists every placement fleet-wide with its site/floor, so the floor editor's palette can grey out an already-placed camera without a request per camera. A camera placement additionally carries `Heading`/`Fov` (degrees) for its 2D coverage wedge and `MountHeight`/`Pitch` (metres/degrees) for its 3D coverage cone, all four independently settable via `PUT /api/placements/{id}` (each an optional pointer field, so one edit never resets another), aimed via on-marker handles/inspector or the editor's on-canvas POV drag handles. Placements are myseliasan's own record rather than fetched live from the node, so — unlike the live camera list, which returns nothing when a node is offline — a placement (with a `LastKnownName` snapshot) stays rendered while its node is unreachable. `GET /api/node-floorplan/{nodeId}` (`services.NodeFloorplans`) is the drill-down query behind "Locate on plan": given a node id, it returns the floor plan(s) holding that node's placements (most-populated first) so a camera event from the camera's own context (e.g. the node manager's embedded pages) can jump straight to the right plan with the right marker focused. Clicking a camera marker opens a small, draggable, resizable floating window playing its live footage (with PTZ when supported) and recent events, which in turn open their recorded snapshot/clip in their own floating window (`node_floor_view.js`'s `CameraWindow`/`MediaWindow`) — both toggle small ⇄ maximized without tearing down the underlying WebRTC stream. The geographic view's site markers and a building/outdoor site's `BuildingFloorView` drill-down (per-node camera markers/rail rows) share one status vocabulary: online / warning (cert expiring soon, reusing the Dashboard's existing cert-health signal) / critical (`lost`) / idle (`self-dropped` or legacy/unknown). The frontend renders with OpenLayers (`ol`/`ol-pmtiles`, vendored into `apps/myseliasan/views/react-webpack`), lazy-loaded only when the Map tab is opened. All new endpoints (`/api/basemap` including `/config` and `/download`, `/api/sites` including `/overview`, `/{id}/position`, `/{id}/areas`, `/{id}/floorplans`, `/api/floors` including `/model`, `/image` replace and clear, and `/background`, `/api/placements` (list index, and `/{id}` position/remove), `/api/node-floorplan/{nodeId}`, plus `PUT /api/nodes/{id}/position`/`/building`) are `AuthOnly` and session-gated like every other myseliasan operator route. The `managed_node.lat`/`lon`/`map_placed`/`site_id`, `site.lat`/`lon`/`map_placed`/`icon`/`kind`, `node_placement.heading`/`fov`/`mount_height`/`pitch`, and `floor_plan.design`/`bg_path`/`grid`/`scale`/`wall_height`/`elevation`/`has_plan_image` columns are all added by explicit, idempotent, NULL-backfilling migrations in `app.go`'s `Migrations()` (run before and independently of the `autoMigrate` config flag), not left to the auto-migrator alone, so an upgrade never 500s on a missing column or breaks row scanning on a NULL left by a bare `ADD COLUMN`. Camera placement's exclusivity is likewise backed by an explicit migration (`20260724-03-placement-unique-camera`) that dedupes any pre-existing `(node_id, camera_id)` duplicates and drops orphaned placements *before* adding the `ux_node_placement_camera` unique index, so it can never fail on an existing fleet's data; `site.kind` backfills to `'building'` and `floor_plan.has_plan_image` is backfilled by classifying existing rows (a PNG at the generated-blank canvas's exact dimensions with no background = blank; everything else = a real plan) — see `docs/modules/apps/myseliasan/app/app.go.md`.
- **myseliasan federated identity security**: `UpsertFederated` looks up existing accounts by `ssoUserId` only. The email-fallback path was removed — `myidsan` can emit a non-unique placeholder email (`"admin"`) for multiple accounts, and matching on it would allow a new SSO identity to inherit the role of an existing (potentially privileged) account (account takeover / privilege escalation). A stable, positive `ssoUserId` is now mandatory; a missing or zero id is rejected with an error. New federated users are provisioned with **no role** (`RoleId = 0`) instead of the `viewer` role; they see an "access pending" screen until a superadmin assigns a role.
- Registered apps are stored in `app_registry`; endpoint tier metadata is scoped by `api_endpoint.appCode` for rate limiting.
- Per-client SSO policy is stored in `app_auth_config`, and exact callback allow-list entries are stored in `app_redirect_uri`.
- Browser cross-app login uses MyIDSan `GET /api/auth/authorize`, `GET|POST /api/auth/login`, and `POST /api/auth/token`.
- `POST /api/sso/introspect` validates token/session state for service-to-service fallback (token validity check only; RBAC decisions are local).
- API endpoint metadata includes `accessTier` (`0=DevOnly`, `1=AuthOnly`, `2=Public`) for route classification. The tier does not replace auth/RBAC; `DevOnly` endpoints still require authorization when registered behind protected handlers.
- Browser-readable MyIDSan UI cookies are limited to presentation state such as the active page and table filters, sorters, and page position. They are not authentication or authorization material; identity remains in the HttpOnly JWT cookie and server-side accessrbac checks.
- **Reverse command tunnel (parent→node control channel)**: myseliasan's `ControlServer` accepts node-initiated WebSocket-over-fleet-mTLS connections on a dedicated port (code fallback `49533`; shipped `config.json` sets `pairing.controlPort` to `39533`). `/api/nodes/{id}/proxy/<node-path>` on myseliasan forwards a tunneled `control.Request` to the connected node; the node's `ControlDispatcher` re-injects it into the node's own API router with a synthetic principal (role from the parent's per-node access grant) and returns **all** response headers (not just `Content-Type`) back through the tunnel. Node-pushed event frames (kind `"notification"`, `"going-offline"`) are ingested into the control plane's unified notification feed via `republishNodeNotification`, which dedups on the node's stable engine id (`infra/notification.Notification.ID`, persisted server-side under `domain/notification.OriginIDKey` = `"__oid"`) so the same event is never published twice. This id is what makes **replay-on-reconnect** safe: because the live push can drop an event published while the channel was down with nothing to backfill it, `ControlServer.SetOnConnect` fires a callback the moment a node's connection is (re)accepted that pulls that node's `GET /api/notifications?since=<now-72h>` (the `since` replay endpoint — see `apps/mymatasan/apis/notification.go`/`apps/myiotsan/apis/notifications.go` and `domain/notification.Service.ListSince`, oldest-first, capped 500/page) over the tunnel and re-ingests anything missing; `apps/myseliasan/services.RelayDedup` (a `relayed_notif` ledger keyed `"<nodeId>|<originId>"`) makes this idempotent against events already delivered live or by an earlier replay, and an hourly prune drops ledger rows older than twice the 72h replay window. Per-node grants (`entities.NodeAccessGrant`: `CanRead`/`CanOperate`/`CanWrite`, an escalation ladder normalised on save — `CanWrite` implies `CanOperate` implies `CanRead`) resolve to the role NAME asserted on the tunnel (`viewer`/`operator`/`admin`, mirroring mymatasan's own three roles) and are managed via `GET/POST/DELETE /api/nodes/access` (node owner or superadmin). `GET /api/nodes/access?roleId=ID` returns a role's grants across all nodes for the central RBAC node-access matrix (superadmin-only). Superadmin roles implicitly have full access to every node (no explicit grant needed). The proxy, media, and access-grant APIs now resolve the caller's **live role** via `AccessSessionMidware.CurrentPrincipal` on every request so a just-demoted operator cannot access nodes with a stale superadmin token. If a node's control channel disconnects while a tunneled request is still awaiting its response, `ControlServer` now tracks each pending request's owning node (`pendingReq{ch, nodeID}`) and, on disconnect, delivers a nil frame to every waiter bound to that node (`failPending`) so `SendRequest` returns the new `ErrNodeDisconnected` immediately instead of blocking to `controlRequestTimeout`; the proxy maps it to the same `404 node is not connected` as `ErrNodeOffline`. This only fails the waiter fast — it does not know whether a non-idempotent write actually applied on the node before the drop, and there is no tunneled-write idempotency key yet (would need node-side dedup support in `mymatasan`), so such writes are **not** automatically retried. The control channel caps each message at 16 MiB (`infra/control.maxFrameBytes`), which is too small to carry a whole recording clip and doesn't let the clip be seeked end-to-end; `GET /api/nodes/{id}/recording-stream/{segId}` (registered before the generic proxy) bridges this by capping each browser `Range` request to an 8 MiB chunk, forwarding it to the node's now-Range-capable `GET /api/recording/segments/{id}/download` (`apps/mymatasan/apis/recording.go`), and returning `206 Partial Content` — the node materializes a seekable plaintext (optionally H.264-transcoded) temp copy of encrypted/HEVC segments the first time a Range request touches them (`segmentPlayFile`, `os.TempDir()/mymatasan-playcache`, swept after 1h) so `http.ServeContent` can serve arbitrary ranges of them.
- **myseliasan self-RBAC**: myseliasan owns its own user store (`control_user` table: local stock superadmin + federated myidsan users) and uses the shared accessrbac core for its own admin endpoints. On first startup, a local stock superadmin is seeded (credentials from `localAuth.username`/`localAuth.password` in config, defaults `admin`/`admin`; must change password on first login). The local login handler ensures the issued JWT carries a non-empty `Email` claim (falls back to `username` when the account has no real email) so the shared auth middleware's empty-email check does not reject the session. After a real superadmin is elevated (`POST /api/rbac/users/{id}/elevate`), the stock account should be manually disabled. Role and permission-matrix management is the shared `/api/access-rbac` surface; user management and handoff are at `/api/rbac/users/*` (superadmin-only). `POST /api/rbac/users/{id}/role` accepts `roleId: 0` to revoke a role (pending state); superadmin self-role changes and self-elevation are rejected. `GET /api/session/me` resolves `roleId`, `roleName`, `isSuperadmin`, and `permissions` live from the user store and includes `pending: true` when the user has no role assigned. The SPA's Roles admin page (`RolesAccessPage`) merges the former separate Roles list and RBAC permission-matrix pages into one: creating a role auto-seeds it with a **viewer default** (read-only `GET` on `/api/nodes` + `/api/notifications`, plus read-only access grants on every currently-adopted node — a snapshot, not a live rule, so nodes adopted later still need a manual grant), a **Copy** action duplicates a role's full permission matrix and per-node access grants onto a new one, and per-role access is set through curated feature toggles (**View fleet**, **Manage fleet**, **Notifications**) that merge verbs onto the underlying `/api/nodes`/`/api/notifications` permission rows; the raw path+verb matrix is still available (collapsed) under an **Advanced** disclosure for edge cases. It also includes a central **Node Access** matrix for assigning per-role node access.
- API rate limiting uses a sliding-window counter per endpoint access tier. Redis-backed cache shares counters across instances; in-memory cache is process-local.
- Secrets:
  - `JWT_SECRET` required. On startup an empty, too-short (<16 char), or known-placeholder `jwt.secret` is auto-replaced with a generated 32-byte CSPRNG secret written back into the config file (preserving formatting), unless `JWT_SECRET` is set in the environment.
  - `GOOGLE_CLIENT_SECRET` can be used to supply the Google OAuth client secret when the `login.google` block is present in config; if both the config value and this env var are empty, the Google provider is disabled with a warning (not a fatal error).
  - `GITHUB_CLIENT_SECRET` can be used to supply the GitHub OAuth client secret when the `login.github` block is present in config; same tolerate-and-disable behavior as Google.
- OAuth redirect state is generated per login request and validated against an HTTP-only state cookie on callback.

## Cache Model

- Cache abstraction is runtime-selected via configuration (`default`, `redis`, `inmemory`, or `memory`).
- Primary shared cache backend for multi-instance deployments: Redis.
- `default`, `inmemory`, and `memory` all select the local in-process memory cache.
- Sessions are held in the cache, and the cache is the authority on session validity. Every boot logs a shared-state boundary statement (`infra/apphost.warnSharedStateBoundary`, `shared_state.go`): a shared (Redis) cache confirms the app can run behind a load balancer; a per-process (`inmemory`/`default`/`memory`) cache states plainly that this instance is single-instance only — a second instance behind a load balancer signs users out whenever it is moved, and a restart ends every session. A distributed transaction lock (`transaction.lockProvider=redis`) paired with a per-process cache logs a `WARNING` instead, since a distributed lock only makes sense with more than one instance.
- SSO sessions are cached as `sso:session:<sid>`.
- Readiness includes cache ping to ensure runtime dependencies are available.
- Shared admin cache API is exposed under `/api/cache-service` for key listing and controlled wipe operations.
- API activity is persisted into `api_log` for both authenticated and non-authenticated `/api` requests, including elapsed `durationMs`.
- Successful cache wipe operations are persisted into API logs for operational audit trail.
- Shared API log listing and monthly database row deletion are exposed under `/api/log` for authenticated/RBAC-protected operators.
- Runtime service logs are written as JSON lines to stdout and dated cross-platform log files derived from the configured base path.
- Shared runtime log listing and monthly log-file deletion are exposed under `/api/log-service` for authenticated/RBAC-protected operators.
- Shared telemetry can expose Prometheus-format metrics at the configured metrics path.
- API telemetry records request counts, duration histograms, and slow request counts using a configurable duration threshold.
- `infra/telemetry.Metrics` (`Describe`/`Inc`/`Add`/`Set`/`Observe`, `apphost.Dependencies.Metrics`, never nil) lets any app or shared module record its own counters/gauges/histograms with arbitrary label sets, emitted in the same `/metrics` scrape as the API/coordination series. Naming convention: `kopiv2_*` for metrics emitted by shared infra (app-neutral — e.g. `infra/recording`, `infra/notification`), an app prefix (e.g. `mymatasan_*`) for app-owned metrics. The Prometheus backend caps cardinality per metric name (500 distinct label combinations) and surfaces truncation as a `<name>_series_truncated` gauge rather than silently dropping series unnoticed.
- `mymatasan` uses this to instrument runtime health that was previously invisible outside logs: detector inference latency and frame/alert outcomes (`vision_monitor.go`), camera reachability (`camera_health_monitor.go`), disk usage and recording-pause state (`machine_health_monitor.go`), recorder ffmpeg restarts and segment finalize outcomes (`infra/recording`), and notification delivery outcomes per channel (`infra/notification`).

## Transaction Coordination

- Critical multi-step operations use an application-level FIFO lock before executing the DB/filesystem unit of work.
- Production multi-instance deployments should use the Redis lock provider.
- In-memory locking is available only for single-process development or tests.
- Redis locks use owner tokens and renewable leases so stale owners cannot release another request's lock.
- Wait timeout removes an abandoned waiter from the FIFO queue.
- Stuck timeout emits telemetry when a lock is held longer than expected.
- DB consistency still uses request-scoped `database/sql` transactions; the coordinator serializes access and prevents request races.
- File-storage uploads are staged first, then metadata insert and final file copy run under the same coordinated transaction workflow with compensation cleanup on failure.
- Synchronous upload keeps the existing request/response contract for development and simple callers.
- Async upload creates an `operation_job` row with idempotency key, payload, retry counters, status, deadline, result, and error state.
- The backend worker recovers stale `running` upload jobs, requeues retryable work, and fails/cleans up exhausted jobs.
- The async worker still uses the same FIFO coordinator and request-scoped DB transaction when executing each upload job.
- File metadata carries `securityLvl` and absolute `expiredAt`; upload endpoints can convert countdown expiry fields into `expiredAt` before entering the service.
- Download authorization is enforced in the file-storage service before reading the physical GUID path.
- File expiry is enforced immediately on download and by a scheduler that sweeps expired physical files plus metadata in bounded batches.

## Data and Persistence

- Databases: PostgreSQL, MariaDB, and SQLite.
- Readiness check performs DB ping through `IDbCrud.Ping(ctx)`.
- Repository layer wraps DB errors with `%w` context for diagnostics.
- Startup bootstrap uses entity reflection to create missing database objects and store a schema manifest hash.
- Safe schema updates are additive only by default. An app can additionally register versioned, checksummed, once-only migrations (`infra/db/bootstrap/migration.go`, `docs/DB_BOOTSTRAP_SPEC.md`) for renames/drops/type-changes the additive path cannot express; they run before auto-migrate, and a fresh database baselines them instead of replaying them. A companion drift detector (`infra/db/bootstrap/drift.go`) reports, but never auto-repairs, schema differences neither path can fix (changed column types, columns the entity no longer declares).
- Optional initial data can be supplied through config-driven SQL seed statements when bootstrap seeding is enabled.
- `myidsan` seeds a minimal core identity dataset (`system` group and first-run stock superadmin login account with bcrypt password storage) during bootstrap. The stock superadmin's password is resolved with precedence `LOCAL_ADMIN_PASSWORD` env → `config.localAuth.password` → a generated 16-character per-install password; a generated password is announced once via a console banner and an `INITIAL_ADMIN_LOGIN.txt` recovery file in the data dir (`app/firstrun.go`) and is never silently rotated on a later boot. A `RESET_ADMIN` marker file dropped in the data dir force-resets and re-announces the account on the next start — the lock-out recovery path. A first-run **setup wizard** (SPA, gated on the superadmin having cleared the forced password change) walks through registering the first relying app, an optional LDAP quick-enable, and creating a personal superadmin account to retire the stock one; completion is a single server-side flag (`GET /api/setup/state`, `POST /api/setup/complete`) persisted in the shared `RuntimeSetting` table, mirroring `mymatasan`'s own setup-state contract. The shared accessrbac core (`EnsureBuiltins`) seeds the `superadmin` and `viewer` roles on startup for any app that enables `AccessRbac` in its `SharedAPIConfig`.
- The app seeds wildcard-host endpoint rows with access tiers for protected API modules so rate-limit classification and endpoint catalog metadata are ready on a fresh install. Protected shared management APIs seed as `DevOnly`. Per-endpoint RBAC seed rows are no longer inserted; the bootstrap `superadmin` bypasses the accessrbac matrix entirely.
- `mymatasan` registers app-local `detection_rule`, `alert_event`, `recording_config`, and `recording_segment` entities. Detection rules store camera binding, detection type, polygon JSON, optional rule config JSON, per-rule schedule policy JSON, threshold, minimum frames, cooldown, sound setting, enabled state, and last trigger time. Alert events store the triggering rule and camera, label, confidence, polygon, optional bounding box/snapshot path, metadata JSON, acknowledgement fields, and audit timestamps.

## Configuration Contract

Config source:

- `ENVIRONMENT=dev` -> `apps/<selected-app>/config.dev.json`
- otherwise -> `apps/<selected-app>/config.json`

Home/data directory split (`infra/apphost`, packaged installs):

- `resolveHomeDir` locates the read-only app root (static assets, bundled AI scripts, the default `config.json`): an `<APP>_HOME`/`KOPIV2_HOME` env override, else the app's dev `BaseDir()` if present, else the running executable's directory (packaged/portable installs).
- `resolveDataDir` locates the writable state root (mutable config, database, recordings, logs, encryption key): an `<APP>_DATA`/`KOPIV2_DATA` env override, else it defaults to `homeDir` — a source/dev checkout keeps the single-directory layout unchanged.
- On first boot, if `dataDir` differs from `homeDir` and no config exists yet at `dataDir`, the shipped default `config.json` is seeded (copied) from `homeDir` into `dataDir` so the app has a writable copy to persist secrets/runtime settings back to.
- Relative `fileStorage.path`, `logging.path`, `tls.certPath`/`keyPath`, `sso.caCertPath`, a SQLite `db.db_name`, the recordings/snapshot root, and the AI training data dir all resolve against `dataDir` (`apphost.ResolveWritablePath`), not the app's dev `BaseDir()`.
- `ResolveWritablePath` is upgrade-safe: if the resolved `dataDir` target does not yet exist but a copy is found at the pre-packaging legacy location (CWD-relative, as an unpackaged dev checkout resolved it), the legacy path is returned instead so an upgrade never orphans in-place recordings, keys, or a database. Installed services set `WorkingDirectory=dataDir`, making the legacy path identical to the target (a no-op fallback).
- `apphost.Dependencies.HomeDir` / `DataDir` expose both resolved roots to app modules; `mymatasan` resolves its at-rest encryption key (`secret/atrest.key`) against `DataDir` the same way.
- On Windows, `apphost.Run` (`infra/apphost/run.go` + `service_windows.go`/`service_other.go`) detects whether the process was launched by the Service Control Manager (`svc.IsWindowsService()`) and, if so, runs under `svc.Run` so `sc.exe`/`services.msc` Stop/Shutdown requests trigger the same graceful shutdown as an OS signal elsewhere; an interactive run or any non-Windows OS is unaffected. The Windows installer (`packaging/windows/mymatasan.iss`) registers the service this way, splitting home (`Program Files`) from data (`%ProgramData%\MyMataSan`) via per-service `Environment`.
- `infra/config.LoadAppConfiguration` reads the whole file and retains the raw bytes on `AppConfigModel` (`Raw()`), so an app that owns config blocks of its own can decode them from the identical document. A malformed `config.json` is now an **error** from `LoadAppConfiguration` — it previously discarded the JSON decode error, so a syntax error silently produced an all-zero config that booted on defaults with no indication anything was wrong.
- **Per-app config seam** (Tier 2 phase C, `docs/MYMATASAN_TIER2_PLAN.md`): an app can implement `apphost.AppConfigDecoder` (`DecodeAppConfig(raw []byte, dataDir string) error`) to own config blocks that the shared `AppConfigModel` does not carry. `run.go` calls it once, after the shared config is loaded and normalized and before any route is registered; an error aborts startup. `mymatasan` uses this for its `camera`/`decoder`/`stream`/`vision`/`health`/`recording` blocks (`apps/mymatasan/config`), including resolving the recordings/snapshots root and the YOLO training dir against `dataDir` — path resolution that used to live in `infra/apphost/run.go` and gave the generic host hardcoded knowledge of a vision feature. `myiotsan` uses the same seam for its own `mqtt` (embedded broker enable/listen address) and `telemetry_store` (write-batch size/flush interval/queue depth, raw/rollup retention days) blocks (`apps/myiotsan/config`). The blocks are **not** nested under an `"app"` key — they stay at the top level of `config.json` exactly where they were, so no deployed config file has to change; only ownership of the Go type and the normalization code moved.

Environment overrides (runtime):

- server: `SERVER_HOSTNAMES`, `SERVER_TLS_PORTS`, `SERVER_NON_TLS_PORTS`
- legacy server compatibility: `SERVER_ADDR`, `SERVER_PORTS`, `SERVER_USE_TLS`, `SERVER_ENABLE_TLS`, `SERVER_ENABLE_NON_TLS`
- db: `DB_ENGINE`, `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `DB_SSL_MODE`
- cache: `CACHE_PROVIDER`, `CACHE_TTL_SECONDS`, `CACHE_KEY_PREFIX`, `REDIS_ADDR`, `REDIS_PASSWORD`, `REDIS_DB`, `REDIS_USE_TLS`, `REDIS_CONNECT_TIMEOUT_MS`, `REDIS_OPERATION_TIMEOUT_MS`
- sso: `SSO_ISSUER`, `SSO_AUDIENCE`, `SSO_SESSION_TTL_SECONDS`, `SSO_POLICY_CACHE_TTL_SECONDS`, `SSO_INTERNAL_TOKEN`, `SSO_PROVIDER_BASE_URL`, `SSO_CA_CERT_PATH`, `SSO_CLIENT_ID`, `SSO_CLIENT_SECRET`, `SSO_REDIRECT_BASE_URL`, `SSO_REDIRECT_PATH`, `SSO_AUTH_CODE_TTL_SECONDS`, `SSO_ACCESS_TOKEN_TTL_SECONDS`
- rate limit: `RATE_LIMIT_ENABLED`
- transaction: `TRANSACTION_LOCK_PROVIDER`, `TRANSACTION_LOCK_WAIT_TIMEOUT_MS`, `TRANSACTION_LOCK_LEASE_MS`, `TRANSACTION_OPERATION_TIMEOUT_MS`, `TRANSACTION_STUCK_TIMEOUT_MS`, `TRANSACTION_JOB_WORKER_ENABLED`, `TRANSACTION_JOB_WORKER_FREQUENCY_SECONDS`, `TRANSACTION_MAX_ATTEMPTS`
- secrets: `JWT_SECRET`, `GOOGLE_CLIENT_SECRET`, `GITHUB_CLIENT_SECRET`
- logging: `LOG_ENABLED`, `LOG_PATH`, `LOG_MAX_LINE_BYTES`, `LOG_CLEANUP_ENABLED`, `LOG_MAX_RETENTION_DAYS`, `LOG_CLEANUP_FREQUENCY_MINUTES`
- api log cleanup: `API_LOG_CLEANUP_ENABLED`, `API_LOG_MAX_RETENTION_DAYS`, `API_LOG_CLEANUP_FREQUENCY_MINUTES`
- telemetry: `TELEMETRY_ENABLED`, `PROMETHEUS_ENABLED`, `PROMETHEUS_METRICS_PATH`, `PROMETHEUS_API_DURATION_THRESHOLD_MS`

Server config contract (`server` in app config):

- `hostnames`: host or IP list. Empty or `*` means wildcard bind across NICs.
- `tlsPorts`: HTTPS listener ports. Empty means no HTTPS listener.
- `nonTlsPorts`: HTTP listener ports. Empty means no HTTP listener.
- `ports`, `enableTls`, `enableNonTls`: legacy shared-port mode used only when explicit TLS/non-TLS port lists are empty.

TLS config contract (`tls` in app config):

- `certPath`: certificate path used when any HTTPS listener is enabled.
- `keyPath`: private-key path used when any HTTPS listener is enabled.
- Relative TLS paths resolve from the writable data directory (see home/data directory split above).
- If an HTTPS listener is configured and either `certPath` or `keyPath` does not exist, `apphost` generates a long-lived (10-year) self-signed ECDSA P-256 keypair covering `localhost`, every configured `server.hostnames` entry, and every local IP address, so a fresh install serves HTTPS immediately without manual cert setup. Existing files are left untouched (bring your own cert, or front the app with a TLS-terminating reverse proxy — see `deploy/README.md`).

Database config contract (`db` in app config):

- `engine`: DB engine selector (`postgres`, `mariadb`, or `sqlite`).
- Runtime DB adapter and bootstrap implementation support all three engines.
- For SQLite, `db_name` is a database file path and relative paths resolve from the selected app directory. `:memory:` is supported for tests/dev experiments only.
- SQLite is intended for single-process small-device deployments; use PostgreSQL or MariaDB for multi-instance production deployments.
- `apps/mymatasan/config.dev.json` defaults to SQLite at `./data/mymatasan.db` with the in-process default cache for standalone small-device deployment.
- `pool` (`db.pool` in app config; Postgres and MariaDB only — SQLite ignores it and stays pinned to a single connection, a correctness constraint since concurrent writers to one file deadlock, not a tunable): `maxOpenConns` (default 25 when absent/zero), `maxIdleConns` (default 5; clamped down to `maxOpenConns` if configured higher, since `database/sql` would otherwise silently reduce it while the config kept claiming a number it never honoured), `maxLifetimeSeconds` (default 1800 = 30 minutes), `maxIdleTimeSeconds` (default 300 = 5 minutes), and `unlimited` (explicit opt-in for Go's old unbounded-open-connections behavior; idle/lifetime bounds still apply even when set). Applied via `dbsql.ApplyPool` right after `sql.Open`, before `Ping`, in both engines' `NewDbCrud`. The default matters more than the knobs: `database/sql` defaults to unlimited open connections, so before this existed a traffic burst could exhaust a database server's entire connection budget and take down every other application sharing it; an absent `pool` block now yields the bounded 25/5 default instead.

SSO relying-app config contract (`sso` in app config):

- `providerBaseUrl`: MyIDSan public base URL used by browser redirects and server-side token exchange.
- `caCertPath`: optional PEM CA/certificate bundle for relying-app backend HTTPS calls to MyIDSan; relative paths resolve from the selected app directory.
- `caCertPath` appends trust roots for the token-exchange HTTP client; it does not disable TLS verification. Hostname, expiry, and certificate-chain validation still apply.
- `clientId`: relying app client id registered in MyIDSan `app_auth_config`.
- `clientSecret`: relying app secret; override with `SSO_CLIENT_SECRET` outside local development.
- `redirectBaseUrl`: relying app public base URL used to build the callback URL sent to MyIDSan. It must match a registered `app_redirect_uri` origin.
- `redirectPath`: relying app callback path, default `/api/auth/callback`.
- `authCodeTtlSeconds`: default MyIDSan authorization-code lifetime when a per-client row does not override it.
- `accessTokenTtlSeconds`: default MyIDSan issued-token lifetime when a per-client row does not override it.

`myseliasan` local auth config contract (`localAuth` in `myseliasan/config.json`):

- `localAuth.username`: username for the stock bootstrap superadmin. Defaults to `admin` when empty.
- `localAuth.password`: password for the stock bootstrap superadmin. Defaults to `admin` when empty. Changed on every startup while the account is still stock and untouched (MustChangePassword=true, not Disabled); once the operator has set their own password or the account is retired, config no longer overrides it.
- The stock account carries `mustChangePassword=true`; the accessrbac session middleware blocks requests from this account (returning `password_change_required`) until the password is changed via `POST /api/auth/change-password`.

Standalone `mymatasan` local auth contract:

- `mymatasan` uses app-local HTTP Basic Auth backed by the local SQLite database instead of MyIDSan JWT/RBAC, but authorizes every request against the shared accessrbac role/permission **data model** via its own middleware (`apis.NewRequireRolePermission`) rather than the shared JWT-based session middleware — see `apps/mymatasan/services/rbac.go` for the three built-in roles (`admin`/`operator`/`viewer`).
- On first startup (no local users exist), `EnsureDefaultAdmin` seeds the admin account from the `localAuth` config block: `localAuth.username` (falls back to `admin` when empty) and `localAuth.password` (env `LOCAL_ADMIN_PASSWORD` overrides the configured value; falls back to `admin` when both are empty, mirroring `myseliasan`'s stock superadmin default). The seeded account is always created with `MustChangePassword=true`, so the bootstrap credential — whichever source it came from — is never usable past the first login. Roles are seeded (`services.EnsureRoles`) and existing users backfilled a role (`ILocalUserService.BackfillRoles`) before this seed step runs.
- On subsequent startups (users already exist), `flagDefaultAdminPassword` still force-flags any admin account left on the shipped legacy default (`admin` / `Admin123`) as must-change, protecting old installs that predate the config-driven seed.
- Local user passwords are stored as bcrypt hashes.
- User management is exposed under Settings and `/api/settings/users`; `GET /api/settings/roles` lists assignable roles.
- The app prevents deleting, disabling, or demoting the last active admin user (counted by role, not the legacy `IsAdmin` flag).

Decoder startup-default config contract (`decoder` in app config):

- `mjpeg.ffmpegPath`: ffmpeg executable used only by `mymatasan` MJPEG fallback live view. Empty or `ffmpeg` resolves from `PATH`; use an absolute path when running as a service or on systems where `PATH` differs.
- `mjpeg.quality`: MJPEG encoder quality used for ffmpeg RTSP conversion; lower values are higher quality and higher CPU/bandwidth. Omitted or invalid values default to `7`.
- `mjpeg.threads`: ffmpeg MJPEG output thread count. Omitted or invalid values default to `1` and are bounded for small-device safety.
- `ffmpeg.rtspTransport`: RTSP transport passed to ffmpeg (`tcp`, `udp`, `udp_multicast`, `http`, or `https`); omitted defaults to `tcp`.
- `ffmpeg.hwaccel`: hardware decode mode (`none`, `auto`, `d3d11va`, `dxva2`, `vaapi`, `cuda`, `qsv`, `videotoolbox`, `vdpau`, or `vulkan`). `none` uses CPU software decode and is the safest default.
- `ffmpeg.hwaccelDevice`: optional ffmpeg hardware device/GPU selector.
- `ffmpeg.initHwDevice`: optional ffmpeg `init_hw_device` value for advanced hardware contexts.
- `ffmpeg.videoDecoder`: optional ffmpeg video decoder name such as `h264_cuvid`; empty lets ffmpeg auto-select.
- `ffmpeg.probeSize` and `ffmpeg.analyzeDuration`: ffmpeg input probing limits used for RTSP conversion and frame capture; larger values can improve unusual stream detection at the cost of startup latency.
- `ffmpeg.lowDelay` and `ffmpeg.noBuffer`: low-latency ffmpeg flags used for live conversion; default to enabled.
- Legacy `camera.ffmpegPath` is still read as a migration fallback when seeding runtime settings.
- `decoder.browseRoots`: optional array of extra directories the server-side ffmpeg file picker may browse, on top of the built-in defaults (app dir + `bin/`, user home, OS-specific common install locations). Default empty.
- Runtime settings expose `POST /api/settings/runtime/auto-tune`, which inspects saved camera RTSP track metadata plus local `ffmpeg -hwaccels` output and immediately saves a conservative decoder profile. Hardware decode is selected only for safely verifiable platform paths; otherwise auto-tune keeps CPU software decode.

`mymatasan` startup config blocks (config.json) added for the appliance hardening features:

- `loginSecurity`: failed-login lockout — `enabled`, `maxAttempts` (5), `windowSeconds` (300), `lockoutSeconds` (60), `lockoutMaxSeconds` (900), `failedDelayMs` (500), `notifyOnLockout`. State is in-memory and per source IP; resets on restart.
- `recording.shred`: secure deletion of footage — `enabled` (*bool, default true) and `passes` (int, default 3). When enabled, retention purge and segment deletion overwrite-then-unlink; `enabled:false` (or `passes:0`) reverts to plain unlink. Intermediate `.ts` files removed during remux are not shredded.
- **Recording compression** (`recording.storage`, runtime-editable via Settings → Recording): four levers to shrink footage without hurting performance. (1) **At-rest storage codec** — `codec` (`copy`/`h264`/`hevc`, default `copy`), `quality` (NVENC CQ, default 26), `maxConcurrentEncodes` (shared NVENC session cap, default 2). With a non-copy codec each completed segment is re-encoded **once** on the GPU (NVENC) at remux time; live capture and event clips always stay stream-copy, and a global NVENC semaphore queues encodes so recording is never blocked. The on-disk codec is stored on `recording_segment.codec`. (2) **Playback transcode** — HEVC segments stream as-is to capable browsers (Chrome/Edge with OS HEVC, Safari); incapable browsers (Firefox/older) get an on-the-fly HEVC→H.264 transcode on the serve path (`?transcode=h264`, fragmented MP4, no plaintext copy stored). (3) **Camera-side H.265** — `GET`/`POST /api/cameras/{id}/encoder` pushes a codec + bitrate cap to the camera's own encoder over ONVIF (Media2/ver20, Media1 fallback, change verified by re-read), the zero-host-cost lever; host then stream-copies. (4) Capacity estimate accounts for the added GPU encode load. Requires an NVIDIA GPU (NVENC) for the host-side levers; defaults leave existing installs recording exactly as before.
- **Codec fallback** (`recording.storage.fallbackToCopy`, `*bool`, `nil`/omitted = enabled): guards the at-rest storage codec lever above so a re-encode codec (`h264`/`hevc`) configured on a host without a usable NVIDIA GPU never drops footage. `infra/recording.NVENCUsable` probes each NVENC encoder once (a throwaway 2-frame encode, cached per encoder for the process lifetime) so `infra/recording/rtsp.go`'s remux path can proactively store a segment as plain stream-copy when the probe fails, and also falls back to copy if a re-encode attempt fails at runtime instead of losing the segment. `GET /api/recording/storage/status` reports `{codec, reEncode, nvencUsable, fallbackToCopy, compatible}` for the current config; the mymatasan UI polls it and shows a sticky dismissible warning (deep-linking to Settings → Recording storage) whenever `compatible=false`. The capacity estimator (`CameraCapacityInput.RecordFallbackToCopy`) also treats fallback-covered re-encode as workload-free (no GPU-encode ceiling / no 0-camera cap) since recording is unaffected, just larger on disk than the re-encoded size. Backward-compatible: existing Copy-codec installs are unaffected; existing re-encode installs keep working exactly as before on hosts that do have a GPU.
- `security.encryptAtRest` (default true) / `security.keyPath` (default `secret/atrest.key`): encryption-at-rest for media (recordings, snapshots/alert images, training images) via the reusable `infra/atrest` AES-256-GCM module. The key lives outside the media roots so the factory reset can destroy it (crypto-erase). With encryption off, data is plaintext; pre-existing plaintext is always read transparently (no migration). Model `.pt` weights stay plaintext.
- `security.keyProtector` (`""`/`file` default, `auto`, `dpapi`, `systemd-creds`, `passphrase`) / `security.passphrase`/`passphraseFile`/`passphraseEnv` / `security.recoveryPath` (default `recovery.atrestkey` beside `keyPath`): protects the on-disk master key itself. `auto` picks DPAPI (Windows) or systemd-creds (systemd Linux, TPM2-backed when present) when available, else `file`; `passphrase` (Argon2id) is portable and the recommended choice for Docker. The key is resolved (`apps/mymatasan/app/wire_security.go`'s `openAtRest`) at the very start of `RegisterAppRoutes`, before any other service — if it's missing but an init marker shows one existed here before, the app mounts only a public pre-login recovery gate (`GET/POST /api/system/recovery/gate`, `/unlock`) instead of starting normally, unless `recoveryPath` + a resolvable passphrase let it restore automatically first. Admin endpoints `POST /api/system/recovery/export`/`verify` (Settings → Backup & Recovery) manage the passphrase-protected recovery escrow that backs up host-bound protectors.
- `bootstrap.allowReset` (default false): gates the **Secure Wipe & Reset** factory-reset endpoint (`POST /api/system/reset`, plus `/state` and `/progress`) and its UI button. The reset stops camera services, **destroys the at-rest encryption key (crypto-erase)**, fast-erases all media (instant unlink), closes the app's own DB connection pool (`SystemResetConfig.CloseDatabase`, now implemented by all three `IDbCrud` engines — required on sqlite/Windows, where the file otherwise can't be deleted while this process holds it open) then drops and rebuilds the database (schema + stock seed; the drop itself retries briefly on a lingering Windows file lock via `removeWithRetry`), securely scrubs the freed space (per-volume TRIM/discard then a time-budgeted HDD overwrite — TRIM degrades to a non-fatal warning, not an error, when it needs elevation the process doesn't have), and restarts via the reusable `apphost.Restarter` (the same primitive the in-app self-update apply uses to relaunch into the new binary — see below). While a reset `InProgress()`, a `ResetGate` middleware (registered before auth) returns a clean `503 reset_in_progress` for every protected request instead of letting DB-backed handlers 500 against the closed pool. It is deliberately unstoppable and best-effort: the Postgres drop uses `DROP DATABASE ... WITH (FORCE)` (with a plain-`DROP` fallback for pre-13 servers), and a stage problem (un-erasable file, failed key destroy, wipe error) becomes a non-fatal *warning* — the sequence always drives to a restart (which re-runs bootstrap to finish any interrupted rebuild) rather than aborting. The real wipe guarantees are the crypto-erase and instant unlink; TRIM + scrub are defense-in-depth. `config.json` is not touched (runtime settings live in the DB and reset with it).
- **Dashboard Intelligence analytics** (`domain/notification` Heatmap/Baseline/AnomalyScan/CameraReliability/NoisyCameras, DB-backed): an hourly `notification_rollup` table (`RollupMaintainer`, watermark persisted under the `notification.rollup.cursor` runtime-setting key so a restart resumes instead of re-scanning history) incrementally aggregates the notifications feed. `GET /api/notifications/heatmap` returns a local day-of-week × hour-of-day activity grid; `GET /api/notifications/baseline` returns a per-bucket expected-activity band (robust median ± k·MAD, Poisson floor for sparse slots, trailing 8-week lookback) drawn behind the dashboard's events-over-time chart. A statistical anomaly monitor (opt-in, `anomalyDetection` runtime-setting key — `enabled`, `mode` (`smart`/`manual`), `sensitivity` (k, 1–6, default 3, smart mode), `detectHigh`/`detectLow` (smart mode), `minActivity` (smart mode), `manualUpper`/`manualLower` (manual mode, 0 disables a side), `requireConsecutive`, `cooldownHours`, `checkIntervalMs`) scores each closed hour and raises `analytics.anomaly` category notifications for spikes or "unusual silence": in the default **smart** mode, per camera against its own (weekday, hour) baseline (a normally-active slot going quiet — the tamper/obstruction/offline signal); in **manual** mode (`AnomalyFinding.CameraId == 0`, no history required — usable from day one), against fixed site-wide hourly `manualUpper`/`manualLower` event-count thresholds. Both tiers share the same consecutive-hour-count + per-(camera,direction) cooldown debounce; `GET/PUT /api/anomaly/settings` and `GET /api/anomaly/scan` (on-demand preview, independent of the monitor's own debounce state, running whichever tier `mode` selects) back the Settings UI. Two further no-baseline-required cards round out Dashboard Intelligence: `GET /api/notifications/reliability` (`?from=&to=`, default last 7 days) returns a worst-first **camera reliability scorecard** — per-camera uptime %, offline seconds, incident count, and currently-offline flag, derived by pairing the camera-health monitor's offline/recovery notification events (an open outage at the window's end still counts, extended to `to`); `GET /api/notifications/noise` (same window defaults, `?limit=`) returns the **alert noise ratio** — the top-N cameras by AI-alert (`vision.alert`) volume with their unread count, a proxy for alert fatigue / mis-tuning (a camera firing constantly and being ignored usually needs its rule retuned).
- **Object metadata recorder / Object Search** (`recording_config.metadataEnabled`/`metadataGapSeconds`, per camera; `metadataEnabled` tracks the camera's recording `enabled` flag directly — there is no separate capture toggle, since a metadata sighting with no footage has nothing to link to): logs "what objects each camera saw" as searchable presence-interval rows (`ObjectObservation`), fed by the same object-detector inference the AI rules already run (`vision.ObservationSink`/`ObservationCapable` — no second video decode); a metadata-only camera (no alert rules) still gets exactly one inference pass per sample via `ObserveOnly`. Consecutive sightings of a label coalesce into one interval, closed after `metadataGapSeconds` (default ~5s, surfaced in the UI as the per-camera **"Object sighting cooldown (s)"** field) of absence; each interval also tracks `peakAt`, the frame its `peakBox` (highest-confidence sighting) was captured on. `GET /api/observations` (+ `/labels`) searches presence intervals with `DataTable`-style server-side filter/sort/paging — including multi-select object filtering via the `In` compare operator (`domain/enums/sqldata.In`, value = a JSON array; also implemented in the SQL layer's `IN (...)` clause builder across sqlite/postgres/mariadb) — restricted at the query level to cameras whose continuous NVR recording is on (a detect-only camera logs observations with no footage backing them, so its sightings are excluded rather than surfaced as permanently-stuck "Finalizing…" rows) — each result linked to the recording segment covering it (seeking to `peakAt`, not the interval start, so the drawn box lines up with the object's clearest moment) for click-to-play, or flagged `footagePending: true` when the sighting falls in the camera's still-open (not yet finalized) segment rather than an unrecorded gap. Footage linkage batches segment lookups per page (grouped by camera, one bounded query sweep per camera instead of one per row). `GET /api/recording/segments/{id}/frame?seek=&w=&box=&label=` extracts (and disk-caches) a JPEG thumbnail of a segment at a given second, optionally with the detection box drawn on it (`infra/recording.ExtractFrameJPEG` + `vision.AnnotateJPEG`) — this backs Object Search's per-result footage screenshot (with play + maximize/camera overlay buttons) as well as equivalent screenshot-with-play thumbnails on the Recordings tab and Notifications event snapshots, plus CSV/PDF export of search results. Object Search is a dedicated top-level **Intelligence** nav item in the frontend (alongside Teach and Object Classes, both also promoted to their own Intelligence nav entries). Retention follows each camera's recording `retentionDays` (30-day fallback), purged on the same 6-hourly sweep as recording segments.
- Capacity: `GET /api/capacity` (estimate) and `POST /api/capacity/calibrate` (benchmark the detector) compute how many cameras the host can process across AI/memory/live-view. Recording is a rolling buffer: instead of zeroing the camera count on a small disk, it caps cameras at a ~1-day minimum-retention floor and reports the retention achievable at the recommended count, balancing cameras against retention. When the at-rest storage codec re-encodes (h264/hevc), a "Recording re-encode (GPU)" workload (NVENC sessions × realtime factor) is added; with re-encode enabled but no GPU it reports 0 and flags the misconfiguration **unless `recording.storage.fallbackToCopy` is on (the default)**, in which case the recorder degrades to stream-copy instead of failing, so no GPU-encode ceiling applies and an assumption note explains the degrade instead.
- Manual purge: `POST /api/recording/segments/purge` deletes recording segments already past each camera's `retentionDays` (the same sweep disk-mitigation runs); `POST /api/notifications/purge?olderThanDays=&onlyRead=` deletes old notifications. Both are surfaced as on-demand buttons (Recording page / Notification settings).
- **In-app self-update** (`services.UpdateService`, `apis/system.go`): `GET /api/system/update` reports current/latest version (`updateAvailable`), whether this install can self-update (`canSelfUpdate`), and any in-flight apply state; `POST /api/system/update/check` forces an immediate GitHub Releases check (also run on a 6-hour scheduler); `POST /api/system/update/apply` (admin-only) downloads the matching release archive, verifies its SHA-256 against the release's `checksums.txt`, swaps the binary and `static/`/`ai/` dirs into `HomeDir`, and restarts via `apphost.Restarter`. Self-update is gated off (`canSelfUpdate=false`) when the `MYMATASAN_MANAGED` env var is set to `package` (set by the `.deb`/`.rpm` systemd unit — upgrade via the package manager instead) or `docker` (set by `deploy/Dockerfile.release` — pull+recreate the container instead), or when `HomeDir` isn't writable; it is available on portable archives and the Windows service install.
- **In-app AI runtime installer** (`services.PythonInstaller`, `apis/settings.go`): `GET /api/settings/vision/ai-runtime/status` reports whether a self-contained Python + torch + ultralytics runtime is installed; `POST /api/settings/vision/ai-runtime/install` (admin-only) downloads a pinned astral `python-build-standalone` interpreter into `DataDir/pyruntime`, pip-installs a GPU (CUDA) or CPU PyTorch build (GPU-detected via `nvidia-smi`) plus `ultralytics`, and persists the resolved interpreter path into `vision.detector.command`; `GET /api/settings/vision/ai-runtime/install/status` polls the job. This is separate from the existing Train-in-app "Install GPU support" flow, which upgrades the Python the detector already uses rather than installing one from nothing. `PythonStatus` now probes the AI runtime the app will *actually* use, not just the bundled one: it checks the configured `vision.detector.command` first (resolved via `PATH` if not absolute) and falls back to the bundled `pyruntime` interpreter, reporting whichever candidate is both present and has `ultralytics` installed — so a "bring your own Python" `vision.detector.command` setup no longer falsely reports "not installed" just because the bundled runtime was never downloaded.

Vision line-crossing rule config contract (`ruleConfig` on `mymatasan` detection rules):

Machine (host) health monitor contract (DB-backed `machineHealth` settings, edited in Settings → Machine Health, applied live):

- Samples host CPU, memory, and disk usage on `intervalMs` via gopsutil. Disk volumes monitored are auto-detected from the paths the app writes to (working dir, recordings/snapshot dir, log dir, per-camera recording storage) plus any user-defined `disk.paths`, deduplicated per underlying volume.
- Each metric has `warnPercent`/`criticalPercent`. A debounced state machine raises a Warning/Critical notification (system category) only after `sustainedSamples` consecutive breaching samples, and a recovery notice after `recoverySamples` consecutive normal samples — mirroring the camera health monitor's debounce.
- Disk mitigation (`mitigation.enabled`): at `purgeAtPercent` it triggers an immediate retention purge of expired recordings (throttled to once per 10 min); at `pauseRecordingAtPercent` it pauses NVR recording (recorder stops writing new segments) to stop the volume filling completely; recording resumes once the disk drops below `resumePercent`. Footage is not captured while paused.
- `mitigation.overwriteOldest` (default `false`) trades pausing for continuity: when the disk reaches `pauseRecordingAtPercent`, instead of pausing it deletes the oldest recorded segments across all cameras (ignoring their per-camera `retentionDays`) until usage would drop below `resumePercent`, via `IRecordingService.PurgeOldestSegments(ctx, keepAfter, wantBytes)`. `mitigation.overwriteMinKeepDays` (default `1`, range 1–365) is a safety floor — footage newer than this many days is never auto-deleted. If a wipe attempt frees nothing (all remaining footage is inside the keep floor), the monitor falls back to pausing recording as before; while paused with overwrite enabled, it keeps retrying the wipe (throttled to the same ~10 min cadence) so recording resumes automatically once footage ages past the floor. A distinct "Oldest footage overwritten" (warning) notification fires on each successful wipe, separate from the pause/resume notifications.
- Normalization keeps `criticalPercent > warnPercent` and `resumePercent < pauseRecordingAtPercent`. The recorder exposes `Pause()`/`Resume()`/`IsPaused()`; resume restarts recorders from their retained configs.

## Versioning Model

- Core version and app version are stored separately as standard `major.minor.patch` SemVer values.
- Core version covers reusable/shared code such as `infra`, `domain`, and shared API/service modules.
- App version covers the selected app module, such as `apps/mymatasan` or `apps/myidsan`.
- The server loads an embedded manifest from `infra/versioning/version.json`.
- The runtime endpoint returns only the selected app version plus the core version; it does not expose the full app version map.
- GitHub Actions consumes pending JSON changelog entries from `changes/pending/.../change.json`, bumps the manifest, and moves processed entries to `changes/applied`.
- Pending changelog entries support the legacy `level/scope/app` shape and a multi-target `type/scope` shape. Multi-target scopes are comma-separated and can include core aliases plus app names from the manifest.
- When a version bump on `main` changes the `mymatasan` app version, `.github/workflows/main.yml`'s `version` job also tags the commit `v<mymatasan-version>` and pushes it (skipped if that tag already exists, e.g. a bump that only touched core or another app), then calls the reusable `.github/workflows/release.yml` in the same workflow run (`workflow_call`, so no PAT is needed — a tag pushed with `GITHUB_TOKEN` alone would not trigger a separate workflow run). `release.yml` checks out the tag, runs GoReleaser (cross-compiled binaries + archives + `.deb`/`.rpm` + multi-arch Docker images per `.goreleaser.yaml`, whose `before.hooks` first runs `packaging/gen-winres.sh {{ .Version }} mymatasan` to embed the brand icon + version metadata into the Windows binaries via `goversioninfo`), extracts the newest `CHANGELOG.md` entry as the GitHub Release notes, and — in a follow-on `windows-installer` job — runs the same `packaging/gen-winres.sh` step before `go build` and then builds the Windows x64 service installer (`packaging/windows/mymatasan.iss` via Inno Setup, which also sets the installer's own icon and shows a finish page with the console URL and, on a fresh install, a generated bootstrap admin password) and uploads it to the same release. `release.yml` is also invokable manually (`workflow_dispatch` with a `tag` input) to rebuild a release. This is the repo's **"latest"** release (`gh`/GoReleaser default), which is what mymatasan's in-app self-updater (`apps/mymatasan/services/update.go`) reads via `GET .../releases/latest`.
- The `version` job independently evaluates `myseliasan` the same way, but tags it in a **separate namespace** — `myseliasan-v<version>` — so the two products never collide and a bump to one never blocks or forces a release of the other (both are evaluated every run; the mymatasan check does not early-exit past the myseliasan one). When the tag is new, the job calls the reusable `.github/workflows/release-myseliasan.yml` (also `workflow_call`, its own `tag` input). That workflow runs GoReleaser against `.goreleaser.myseliasan.yaml` and then a `windows-installer` job (`packaging/windows/myseliasan.iss`, `packaging/gen-winres.sh {{ .Version }} myseliasan`) exactly like mymatasan's, with two differences: it publishes with **`gh release create --latest=false`** (myseliasan must never become the repo's "latest" release, since that is what mymatasan's updater reads — a suffix-only asset match there would otherwise let a myseliasan archive get installed over mymatasan; see `apps/mymatasan/services/update.go`'s `mymatasan_` asset-prefix guard, the second independent safeguard), and it does not let GoReleaser create the GitHub Release itself (`release: disable: true` in `.goreleaser.myseliasan.yaml`) — GoReleaser OSS cannot derive a semver from a prefixed tag (that's a Pro-only `monorepo`/`tag_prefix` feature), so the workflow exports `GORELEASER_CURRENT_TAG=v<version>` for GoReleaser's own artifact naming, runs it with `--skip=validate` (the checked-out tag deliberately does not match `GORELEASER_CURRENT_TAG`), and then calls `gh release create` itself under the real `myseliasan-v<version>` tag.
- The `version` job independently evaluates `myiotsan` the same way — its own tag namespace, `myiotsan-v<version>`, also `--latest=false`, also `release: disable: true` in `.goreleaser.myiotsan.yaml` with `GORELEASER_CURRENT_TAG`/`--skip=validate`/self-published via `gh release create`, calling the reusable `.github/workflows/release-myiotsan.yml`. It does the same again for `myidsan` — tag namespace `myidsan-v<version>`, also `--latest=false`, also `release: disable: true` in `.goreleaser.myidsan.yaml` with the same `GORELEASER_CURRENT_TAG`/`--skip=validate`/`gh release create` pattern, calling the reusable `.github/workflows/release-myidsan.yml`. **Only `mymatasan` may ever be the repo's "latest" release** — its in-app updater is the only one of the four that reads `releases/latest` and matches assets by a product name prefix (`mymatasan_`); if a `myseliasan-v…`, `myiotsan-v…`, or `myidsan-v…` tag ever became "latest", that updater would find no asset it recognizes and every deployed node would silently stop receiving updates. This is a starvation failure mode, distinct from (and not prevented by) the asset-prefix guard, which only stops a node overwriting itself with the *wrong* product's binary once it does find a release. All four products (`mymatasan`/`myseliasan`/`myiotsan`/`myidsan`) are evaluated every run without early-exiting past an earlier one, so any combination can release from a single push.
- `myiotsan` additionally opens a new listening port no other product in the suite does: an embedded MQTT broker on `1883/tcp` (`mqtt.addr`, plaintext, LAN). Its Windows Inno installer (`packaging/windows/myiotsan.iss`) adds a Windows Firewall rule for that port; without one the app comes up healthy and no device ever connects, which presents as "broken devices" rather than "blocked port". Neither `myiotsan` nor `myidsan` has a self-updater — unlike `mymatasan`, nothing inside either running app checks `releases/latest`; updates are manual or package-manager-driven.
- `myidsan`'s Windows Inno installer (`packaging/windows/myidsan.iss`) installs to port `3001`, data root `%ProgramData%\MyIDSan`, and registers the service via `sc.exe` like the other products; it additionally offers a "reset admin login" tick-box that drops a one-shot `RESET_ADMIN` marker consumed on next start, mirroring the `.deb`/`.rpm` postinstall's first-run login banner.
- `.github/workflows/installer-check.yml` (push/PR CI, no release) compiles every product's `.iss` script against a placeholder binary as a fast syntax check (matrix over `mymatasan`/`myseliasan`/`myiotsan`), so an Inno Setup Pascal Script slip is caught before it would fail a real release.
- `.github/workflows/go-check.yml` (push/PR CI, no release): `go build ./...`, `go vet ./...`, and `go test ./...` on every push/PR, plus an advisory (non-blocking) `govulncheck ./...` step. This is the suite's first Go build/test CI gate — previously nothing ran the test suite automatically, so a stale/broken test could sit failing unnoticed on `main` (which is exactly what this workflow caught and fixed in `infra/apphost/run_test.go` on introduction).

## API Documentation Contract

- `GET /swagger`: Swagger UI.
- `GET /swagger/openapi.json`: OpenAPI 3.0 document.
- Endpoint list is generated from runtime route registration, so shared and app-local APIs are documented from one source.
- Key endpoints include reusable request/response schema components (`components.schemas`) for FE integration and code generation.
- Key list/create/update endpoints are mapped to endpoint-specific response wrappers (typed `result` payloads) instead of only generic default/paging contracts.
- Shared DB-backed list endpoints expose `limit`, `offset`, and optional `filters`/`sorters` query parameters so paging can be filtered and ordered in the backend before the response is returned. `filters` and `sorters` accept JSON object or array values, with repeated `filter` and `sorter` query parameters also supported. Multiple filters are combined with `AND`; multiple sorters keep the request order.
- Non-JSON endpoints are explicitly modeled with route-accurate status/content (for example OAuth redirect `302` and binary file download `application/octet-stream`).
- Cache admin endpoints are documented with `cache-service` tag (`GET /api/cache-service`, `GET /api/cache-service/health`, `DELETE /api/cache-service`, `POST /api/cache-service/wipe`).
- API log endpoints are documented with `log` tag (`GET /api/log`, `DELETE /api/log`).
- Runtime log endpoints are documented with `log-service` tag (`GET /api/log-service`, `DELETE /api/log-service`).
- Runtime version endpoint is documented with `system` tag (`GET /api/version`).
- File-storage sync upload, async upload, download, inline view, and job status endpoints are documented with `file-storage` tag.
- Shared JSON response wrappers include top-level `durationMs` for elapsed request handling time in milliseconds.
- Prometheus telemetry includes transaction lock event, wait-duration, and stuck-lock metrics using low-cardinality labels.
- App modules can provide richer endpoint summaries/descriptions by implementing the shared API docs provider contract.

## Application Metrics Principle

App-specific metrics registered via `deps.Metrics` (`telemetry.Metrics`) follow one rule:
**instrument what FAILS SILENTLY.** A metric that duplicates a log line an operator would already
read is noise; a metric for a failure mode with no other symptom — nothing else logs it, nothing
else changes in the UI — is the whole point, and its help text (`Describe`) says what a rising or
falling value means for the operator to act on.

- `infra/safego` (shared, every app): a supervised goroutine that panics is caught and restarted
  — the app stays up — but the only other trace was one log line, and a crash-looping subsystem
  looks identical from outside to a healthy one. `infra/apphost/run.go` wires
  `<app>_task_panics_total{task}` to `safego.SetPanicObserver` for every app at startup. See
  `docs/modules/infra/safego/safego.go.md`, `docs/modules/infra/apphost/run.go.md`.
- `myiotsan` (a live scrape showed 0 app series before this): the ingest pipeline is deliberately
  arranged so a publish never touches the database and so never raises an error a human sees.
  `myiotsan_ingest_dropped_total` is the headline — a reading shed because the write queue was
  full is silent data loss (the broker keeps accepting, the UI keeps rendering, nothing is
  logged). See `docs/modules/apps/myiotsan/services/metrics.go.md`.
- `myseliasan` (a live scrape showed 0 series before this): a control plane is a relay with no
  sensors of its own, so its failures are fleet failures and they are the quietest kind — a node
  dropping off the control channel looks in the UI identical to one an operator released; a
  certificate creeping toward expiry has no symptom until the day it expires. See
  `docs/modules/apps/myseliasan/services/metrics.go.md`.
- `mymatasan` was already instrumented before this round (vision frames/inference/alerts, camera
  health, disk, and recording's segment-finalize outcomes / ffmpeg restarts —
  `docs/modules/infra/recording/types.go.md`); it is not a gap this round closed.

## Non-Goals

- Not a monolithic framework generator.
- Not optimized for distributed stream processing across nodes.
- Not a general-purpose schema migration framework (e.g. no down-migrations, no CLI
  generator) — `infra/db/bootstrap/migration.go` covers the narrower, appliance-specific
  need: versioned up-only migrations for what additive auto-migrate cannot express, run
  automatically at startup.
