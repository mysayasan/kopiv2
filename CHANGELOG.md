## 2026-07-21 — myiotsan 0.21.0, mymatasan 1.111.0, myseliasan 1.36.0, core 1.64.0 (db914b1)

### Added

- **myseliasan**: Fleet Map / GIS: a new offline geographic + indoor spatial view of the adopted node fleet, rendered with OpenLayers (vendored into the myseliasan frontend, lazy-loaded so it never weighs down the initial bundle) and a self-hosted Protomaps .pmtiles basemap served by a new Range-served handler (GET /api/basemap/info, GET /api/basemap/tiles.pmtiles) - no tile CDN, so it works on an air-gapped/intranet install like the rest of the app. The Geographic view plots nodes at lat/lon (new ManagedNode.Lat/Lon/MapPlaced fields, set by dragging a pin via PUT /api/nodes/{id}/position) and colors each pin online/warning(cert expiring)/critical(lost)/idle, matching the existing Dashboard cert-health signal. The Floor plans view lets an operator create sites and add a floor plan per site either by uploading an image (PNG/JPEG/GIF, up to 24 MiB) or by drawing one from scratch in a new built-in floor designer (rooms/walls/text/pen tools, grid-snap, undo/redo, multi-select, rotate/flip, pan/zoom) whose vector shapes round-trip through a new FloorPlan.Design field so a drawn plan can be reopened and re-edited; an uploaded photo can likewise be annotated later, with its pristine original preserved as a new FloorPlan.BgPath background layer (GET /api/floors/{id}/background) so re-editing never draws over an already-flattened render (POST /api/floors/{id}/image replaces the rendered image + design). Nodes/cameras are dragged onto a plan as NodePlacement rows keyed to pixel position on the plan image, myseliasan's own record with a name snapshot so a marker stays visible even while its node is offline; a camera placement now also carries a Heading/Fov coverage arc (degrees), aimed via on-marker handles and drawn as a translucent wedge on the plan so an operator can see which part of a room a camera actually watches. A new GET /api/node-floorplan/{nodeId} drill-down backs a 'Locate on plan' action from a camera event on the geographic view, jumping straight to the right floor plan with the right marker focused; clicking a camera marker opens a small, draggable, resizable floating live-view window (with PTZ when supported) whose recent events open their recorded snapshot/clip in their own floating window, all toggling small/maximized without restarting the underlying WebRTC stream. New/extended endpoints, all AuthOnly and session-gated the same as every other myseliasan operator route: /api/basemap, /api/sites, /api/floors (incl. POST .../image replace and GET .../background), /api/placements (incl. heading/fov), /api/node-floorplan/{nodeId}, and PUT /api/nodes/{id}/position.
- **myseliasan**: Node mTLS certificate renewal on the myseliasan fleet control plane is now operator-gated per node instead of renewing automatically and silently forever. A new ManagedNode.AutoRenew flag (default off for newly adopted nodes) must be enabled by an operator, via a new toggle on the node's Details tab or PUT /api/nodes/{id}/auto-renew, before the control plane's Enroll endpoint will honour a renewal re-enrollment from that node (the node still authenticates with its existing pairing token and needs no claim code; only the control plane's willingness to sign changed). Initial enrollment right after adoption is never gated. A node whose operator never turns this on simply lets its certificate lapse on schedule, drops off the control channel, and goes lost -- a per-node dead-man's switch so a forgotten or decommissioned node falls out of the fleet without anyone having to remember to explicitly revoke it. The fleet-health 'certificate expiring' warning now fires only for nodes with auto-renew off (an auto-renew-on node's renewal will be honoured, so its approaching expiry is not actionable). Node certificate default lifetime was raised from 7 to 90 days (pairing.certTtlHours, shipped config.json now sets 2160) so an un-renewed node stays reachable for a meaningful window, and the control-plane cert-expiry warning window (pairing.renewBeforeHours) was raised to 336 hours (14 days) in the shipped config to match.
- **myseliasan**: Extends the myseliasan Fleet Map (shipped as a single-node-pin geographic view) into a building-oriented digital twin: a Site now carries its own Lat/Lon/MapPlaced and an operator-chosen icon glyph, so a building - not the appliance that happens to record its cameras - is what anchors cameras on the geographic map. GET /api/sites/overview rolls up every building for the map (worst status among the nodes with cameras inside it, plus per-camera unread-notification counts via a new GET /api/notifications/tally, so one node recording cameras in several buildings is never double-counted onto all of them). A node can be dragged onto a building (or picked from a 'needs a home' list) to record that it physically resides there (PUT /api/nodes/{id}/building, ManagedNode.SiteId); a building-resident node stops drawing its own map pin and is represented by its building's marker instead. Clicking a building marker opens a new building-scoped floor-plan drill-down (GET /api/sites/{id}/floorplans, BuildingFloorView) showing every floor with every camera on it regardless of which node owns each one, each marker/coverage-wedge colored and streamed by its own owning node - distinct from the existing node-scoped floor view. The indoor floor-plan editor gained a proper create/edit building dialog (name + curated emoji icon picker, replacing a bare name prompt), pan/zoom + a select/delete toolbar for the plan canvas, keyboard delete/escape for the selected marker, and flags a placement as a 'ghost marker' when its camera no longer exists on an online, reachable node. The camera live window can now open a recorded event's snapshot/clip inline over the same live panel (a Back button returns to live without tearing down the underlying WebRTC stream). The offline basemap moved from a single .pmtiles archive to a directory of region archives (GET /api/basemap/tiles/{name}, region bounds parsed straight out of each PMTiles header) so a fleet spanning disjoint areas is served as several region files instead of one planet-sized archive, and gained an optional, off-by-default on-demand region download (POST /api/basemap/download, gated behind an operator- or env-configured remote pmtiles source plus the pmtiles CLI tool) - the one action in this otherwise air-gapped app that can reach the internet, and only when explicitly configured.
- **mymatasan**: Added a source-camera filter dropdown to the mymatasan Notifications page, alongside the existing Unread/All and category-type chip filters. Picking a camera passes cameraId straight through to the already-camera-aware GET /api/notifications endpoint (the backend already supported this parameter; only the UI was missing it), narrowing the feed to that camera's own AI-detection and camera-health notifications - the only notification kinds that carry a cameraId, so machine-health/login-security rows are naturally excluded once a specific camera is picked. Useful on any install with more than a couple of cameras, where the unified feed otherwise interleaves every camera's events together.
- **myseliasan,mymatasan,myiotsan**: Fixes a gap where the myseliasan fleet control plane undercounted a node's notifications: it only relayed events pushed live while a node's control channel was connected, so anything the node raised during a disconnect was dropped with no backfill. Node builds (mymatasan and myiotsan) now accept a since=<unix seconds> query param on GET /api/notifications that returns that node's own notifications oldest-first from that time (domain/notification.Service.ListSince, capped 500/page); the persisted notification metadata now also carries the node's stable engine id (domain/notification.OriginIDKey = "__oid") so a pulled row and a live-pushed one share one dedup key. On myseliasan, ControlServer now fires an onConnect callback the moment a node's control connection is (re)accepted, which pulls that node's notifications from the last 72 hours over the tunnel and re-ingests anything missing; a new relayed_notif dedup ledger (services.RelayDedup) makes this idempotent against events already delivered live or by an earlier replay, and an hourly job prunes ledger rows outside twice the replay window. This is scoped to all three apps together (not just myseliasan) because the parent-side replay only works against a node build new enough to serve the since= endpoint -- deploying only the myseliasan half would silently no-op the replay against every existing node.

### Changed

Two new feature cards were added: 'Fleet maps & floor plans' (the myseliasan control plane now maps sites/buildings and edge nodes geographically, with an in-app per-building floor-plan designer, camera placement with field-of-view coverage cones, a building view aggregating multiple nodes' cameras, and click-to-locate / live view from the map) and 'Face recognition' (mymatasan edge nodes enroll known people and turn a detection into a named alert, entirely on-prem). ### Fixed

- **myseliasan**: Fixed two related node-adoption control-channel gaps that could leave a mymatasan/myiotsan node effectively unmanageable from the myseliasan control plane. First, if a node's adopt call succeeded but the control plane then failed to save the resulting ManagedNode row (a DB hiccup or schema mismatch), the node had already committed to pairing and burned its single-use claim code - it was left permanently stranded, invisible to discovery and unable to retry. NodeRegistry.Adopt now best-effort rolls back the node's own pairing in that case (so it becomes discoverable and adoptable again) and returns a new ErrAdoptPersist with an actionable operator-facing message instead of a raw database error, while the raw cause is still logged server-side. Second, a node that already holds a valid fleet-CA certificate but has no managed record (e.g. released here without being reset on the node) kept dialing the control channel and being silently refused forever, with no operator-visible symptom beyond a repeating log line. ControlServer now tracks each refusal (deduped by node id, bounded at 200 entries) and a new Unrecognized nodes panel in the Nodes UI lists them (GET /api/nodes/unrecognized) with Block (POST /api/nodes/{id}/block, revokes the certificate via a new RevokeNode registry method that needs no managed row) and Dismiss (POST /api/nodes/{id}/forget) actions. AcceptControlConn was also reordered to check certificate revocation before the row lookup, so a blocked-but-row-less node correctly reports as revoked rather than a generic unknown node that would make Block appear to do nothing.
- **myseliasan**: Fixed a bug where a camera's notification events could silently go missing from its floor-plan live window (CameraWindow) once that node had enough recent activity across all its cameras: the window fetched the owning node's whole notification feed (capped at 60 rows) and filtered to the one camera client-side, so a camera's older events fell off the page the moment other cameras on the same node generated enough notifications to push them past the 60-row limit - while the badge count (which tallies the full unread set server-side) kept showing the true, larger number, so the list and the badge visibly disagreed. GET /api/notifications now accepts a cameraId query parameter that scopes the list server-side (in addition to the existing nodeId scope). The floor-plan CameraWindow now reads the OWNING NODE's own notification feed for that camera live over the control-channel proxy (falling back to the control plane's relayed feed only when the node is unreachable), because the control plane holds only the notifications that streamed up while the channel was connected whereas the node keeps its full history - so the window shows the node's authoritative list instead of the relayed subset. Footage and snapshots already resolved from the node over the same proxy, so their ids line up.
## 2026-07-17 — mymatasan 1.109.0, core 1.63.0 (bd663c9)

### Added

- **mymatasan,infra**: Face recognition: a new global-gallery enroll->recognize feature, the detect-embed-match sibling of LPR, built as a stacked detection stage rather than the singleton custom-YOLO slot so it coexists with a trained model. Admins enroll named people once (People tab / POST/GET/PUT/DELETE /api/faces, one or more clear front-facing photos per person) into a gallery stored as encrypted embeddings (AES-256-GCM via the existing at-rest cipher, base64 TEXT so it stays portable across sqlite/MariaDB/Postgres); enrollment refuses an image with zero, multiple, low-quality, or too-small faces so a bad photo can never silently poison future matches. A new detection rule mode (detectionType: "face") fires on any recognized person (matchMode: known, the per-camera toggle's default), a chosen watchlist (include + a people list), or unrecognized strangers only (unknown), gated by a minConfidence floor (default 0.6) below which a marginal match is treated as unknown rather than risking naming the wrong person. Recognized identity (personId, personName, faceConfidence, recognized) is promoted to top-level alert metadata for notification templates, same pattern as LPR's plate metadata. The worker (OpenCV YuNet detect + SFace 128-d embed, both permissively licensed, both already-available-dependency opencv-python/numpy - zero new heavy dependency) shares the same high-resolution per-camera capture gate LPR already uses (WantFace, alongside WantLPR) so cameras without a face rule pay no extra capture or compute cost. setup.ps1 gained a -Faces switch that installs the Python deps and downloads the two .onnx model files.

- **myiotsan**: Added a Flow Engine to myiotsan: a Node-RED-style visual, executable data-flow canvas for wiring telemetry into computed values, alerts, and (guarded) actuation, shipped across four phases (P1 engine, P2 canvas, P3 templates + derived metric, P4 rate-limiting + MQTT bridge-out + editor polish). A flow is a new entity (`IotFlow`, `apps/myiotsan/entities/iot_flow.go`) storing a node/wire graph as one JSON document, authored on a new admin-only frontend page (`apps/myiotsan/views/react-webpack/src/views/components/flows.js`): a flow list plus an SVG drag-and-drop canvas (palette, wiring, per-node config panel, zoom), reachable from a new "Flows" entry under the Automation nav group and new i18n keys (`flows.*`) in all four locales. The node palette (`apps/myiotsan/services/flows.go`) covers an input (`device_telemetry`, emits on a new reading), transforms (`scale`, and `function`/`expression`/`switch` -- arbitrary JavaScript), logic (`threshold`, `deadband`, and `throttle` (P4) -- passes at most once per N seconds, dropping anything inside the window), and outputs (`debug` for the live inspector, `notify` to raise an alert, `command` to actuate, `derived_metric` (P3) to persist a computed value as a new telemetry series, and `mqtt_out` (P4) to publish the payload to an MQTT topic via the embedded broker -- data outward, never a device command, so it does not go through the actuation gate). `parseGraph` validates every graph at save and again at compile: closed node-type set, no dangling wires, no cycles, a 200-node sanity ceiling. `services.FlowRuntime` (new `apps/myiotsan/services/flow_runtime.go`) compiles a graph and runs it on its own worker goroutine, tapping the SAME decoded-sample stream `RuleService.OnReading` does (new `Ingest.SetFlows`/`ingest.go`'s `handleSamples` tap) without ever blocking ingest (events are dropped under backpressure, counted, never queued unboundedly), and reconciling compiled flows against the database on a ticker plus an explicit change signal so an edit/enable/disable takes effect with no restart -- the same pattern the Modbus poller already uses. The `function`/`expression`/`switch` nodes run in a brand-new embedded, sandboxed JavaScript interpreter (`github.com/dop251/goja`, new pure-Go dependency, isolated in `apps/myiotsan/services/flow_eval.go`) with NO host bindings at all (no filesystem, network, `require`, or `os`) and a hard 100ms-per-call watchdog that interrupts a runaway script -- both guarantees are pinned by tests that try to escape the sandbox and that drive an infinite loop. The safety invariant that makes 'a flow can run arbitrary JavaScript' acceptable: only the dedicated `command` output node can actuate, and it routes through the SAME guarded `CommandService.Issue` chokepoint every manual command, scene, and schedule already uses (actuation-enabled, admin-only, declared bounds, rate limit, full audit, never auto-retried) -- an arbitrary-JS node can shape a *value* but cannot skip a gate, retry a refusal, or reach a device the command layer would otherwise refuse. This is a deliberate, later reversal of `docs/MYIOTSAN_PLAN.md` §8g's original 'no visual node-graph editor' scope line (now documented as §8i, with the reversal called out at §8g and in §9's risk table). P3 added slot-based templates -- a device named by a placeholder (`"$inverter"`) instead of a concrete key makes a flow reusable; `GET /api/flows/{id}/slots` reports what a flow declares and `POST /api/flows/{id}/instantiate` binds every slot to a real device, stamping out a concrete, disabled-by-default copy for an admin to review and enable -- and a shipped builtin 'Solar system' template flow (`apps/myiotsan/services/flow_catalog.go`, seeded idempotently at boot like a device profile) demonstrating the one thing the data-flow model exists to do: combine two telemetry streams (grid + PV power) into a derived self-consumption value via the per-flow JS context, plus a high-grid-import threshold alert. Flow import/export (`.iotflow`, `apps/myiotsan/services/flow_transfer.go`) mirrors the existing `.iotprofile` pattern: an import is never builtin and always arrives disabled. New API (`apps/myiotsan/apis/flows.go`): `GET/POST /api/flows`, `GET/PUT/DELETE /api/flows/{id}`, `POST /api/flows/import`, `GET /api/flows/{id}/export`, `GET /api/flows/{id}/slots`, `POST /api/flows/{id}/instantiate`, `POST /api/flows/{id}/run` (test-fires the flow off the live runtime with a synthetic seed value -- an output node still acts for real, which is the point), and `GET /api/flows/{id}/debug` (the live per-node inspector snapshot). The whole `/api/flows` area is admin-only in the RBAC matrix (`apps/myiotsan/services/rbac.go`) -- unlike scenes/schedules, even READING a flow's graph is denied below admin, because the graph itself can reveal an actuation path. Verified with a dedicated unit suite (`apps/myiotsan/services/flows_test.go`) covering propagation through scale/threshold/deadband, the two JS node types (including the per-flow context surviving across two separate input messages, the mechanism the solar sample depends on), sandbox containment (require/process/filesystem all fail), the watchdog killing a `while(true){}` node within a bounded window, guarded-issuer-only actuation, notification publishing, graph validation rejections, the derived-metric output, and slot detection/substitution/template guards. P4 is a polish pass on the same engine, all in the existing flow files: the `throttle` logic node above is stateful (`compiledFlow.lastPass`, keyed like `deadband`'s state) but deliberately timer-free -- it only ever drops a message inside its window, never defers or replays one later, so it cannot itself become a delayed loop. The `mqtt_out` output node above reaches the broker through a new `mqttPublish` dep (`NewFlowRuntime` gained a `publish` parameter, wired from `app.go` as `broker.Publish`) and renders the payload as its shortest decimal for a number, as-is for a string, or JSON otherwise. `cfgFloat` (`services/flows.go`) was fixed to also parse a string-encoded config value -- a `<select>` field (e.g. `mqtt_out`'s QoS picker) stores its option value as text -- falling back to `strconv.ParseFloat`; payload coercion stays strict, only config reading is this lenient. GoReleaser (.goreleaser.yaml + packaging/stage-archive.sh) builds, from one run: linux/windows amd64+arm64 archives bundling the web UI/AI scripts/default config/service files; .deb/.rpm packages (nfpm) that install to /opt/mymatasan, create a dedicated unprivileged mymatasan system user, and install+manage a systemd unit (deploy/nfpm/mymatasan.service + postinstall/preremove/postremove scripts); and multi-arch Docker images (deploy/Dockerfile.release, ghcr.io/mysayasan/mymatasan) with ffmpeg baked in. To support this, infra/apphost gained a home/data directory split (resolveHomeDir/resolveDataDir, MYMATASAN_HOME/MYMATASAN_DATA or generic KOPIV2_HOME/KOPIV2_DATA env overrides): a read-only app root (static assets, AI scripts, default config) is now resolved separately from a writable state root (mutable config, database, recordings, logs, encryption key), with the default config auto-seeded into the data dir on first boot and all writable paths (ResolveWritablePath) falling back to the pre-packaging legacy CWD-relative location when present, so upgrades never orphan existing recordings/keys/DB. If HTTPS is enabled and no certificate exists yet, apphost now generates a long-lived self-signed keypair on first boot (infra/apphost/selfcert.go) covering localhost, configured hostnames, and every local IP, so a fresh install serves HTTPS immediately; deploy/README.md documents bringing your own cert or fronting with a TLS-terminating reverse proxy. The version-bump pipeline (infra/versioning) now also renders and prepends a dated, Keep-a-Changelog-style CHANGELOG.md entry (grouped by change type) for every applied changes/pending batch, wired into .github/workflows/main.yml. Alongside this, two-way audio talk-back shipped for cameras with an ONVIF audio backchannel (mic button in live view, GET/POST /api/cameras/{id}/talk[/offer], new infra/talk package), the machine-health disk mitigation gained an 'overwrite oldest' mode that deletes the oldest recorded segments (with a configurable keep-days floor) to keep recording continuous instead of pausing, and several camera/AI UI fixes landed: the AI rule Test action no longer force-navigates to the notifications page, the zone/line drawing editor gained a Rotate tool, adding a camera now selects the new camera's node directly, the recording status badge distinguishes a detect-only AI frame source from actual recording, and the credential-gate prompt gained a two-step-confirm Remove camera action plus clearer error styling.
- **mymatasan, apphost, infra**: Completes the installer-packaging plan (phases 4-7) on top of the already-shipped GoReleaser packaging: .github/workflows/main.yml now tags the commit v<mymatasan-version> and pushes it whenever a version bump changes the mymatasan app version, then calls a new reusable .github/workflows/release.yml (workflow_call + workflow_dispatch) that checks out the tag, runs GoReleaser, and extracts the newest CHANGELOG.md entry as the GitHub Release notes. mymatasan gained native Windows service support (infra/apphost/service_windows.go detects an SCM-launched process and runs it under svc.Run so services.msc Stop/Start triggers the same graceful shutdown as an OS signal; service_other.go is the no-op stub elsewhere; run.go's Run is now a thin platform dispatcher over the renamed runApp) plus a new Inno Setup Windows x64 installer (packaging/windows/mymatasan.iss) that installs to Program Files, keeps data in %ProgramData%\MyMataSan, and registers the service via sc.exe; release.yml gained a windows-installer job that builds and uploads it. The r450k marketing site added a live Download page (GET /api/downloads in the Cloudflare Worker reads the GitHub Releases API and edge-caches it) so releases surface without a site redeploy. mymatasan also gained an in-app AI runtime installer (new services/python_install.go, Settings -> AI -> Install AI runtime, GET/POST /api/settings/vision/ai-runtime/{status,install,install/status}) that downloads a self-contained astral python-build-standalone interpreter and pip-installs a GPU (CUDA) or CPU PyTorch build plus ultralytics for hosts with no usable Python at all, distinct from the existing Train-in-app 'Install GPU support' flow; the stock yolo11n.pt model is now bundled in every distribution channel (archives, .deb/.rpm, Windows installer) since only the heavy Python/torch runtime is fetched at install time. Finally, mymatasan gained in-app self-update (new services/update.go, Settings -> Version & Health -> Updates, GET /api/system/update, POST /api/system/update/{check,apply}): it checks GitHub Releases on a 6-hour schedule and on demand, and on installs that own their files (portable archive or the new Windows service installer) downloads the matching release archive, verifies its SHA-256 against checksums.txt, swaps the binary and static/ai assets into place, and restarts via the existing apphost.Restarter.
