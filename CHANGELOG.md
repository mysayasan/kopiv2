# Changelog

All notable changes to this project, generated from `changes/` entries on each version bump. Newest first.












## 2026-07-05 — mymatasan 1.81.1 (fa7922e)

### Fixed

- **mymatasan**: The Windows installer compiles again after the previous fix exposed a second Inno Setup Pascal Script incompatibility: `ISCC` aborted with "Unknown identifier 'Randomize'" because Inno's scripting engine does not expose `Randomize`. The installer generates the first-run admin password with a random draw, so the release `windows-installer` job failed and `mymatasan-setup-<version>-windows-x64.exe` was again not built. Inno's own `Random` is unusable here regardless: it is backed by Delphi's global `RandSeed` (initialised to 0) that the script cannot seed, so every install would have produced the identical bootstrap password. The password generator now uses a self-contained LCG seeded from the install-time `GetTickCount` (perturbed by the wall-clock time of day), so it both compiles and yields a distinct one-time admin password per install.
## 2026-07-05 — mymatasan 1.81.0 (a77dd4f)

### Added

- **mymatasan**: New **Teach** wizard lets anyone teach a camera a new detection skill without any AI knowledge — you name it in plain words, pick one of three kinds (**Recognize a new object**, **Tell good from bad**, or **Spot anything unusual**), draw where it appears, then show the camera real examples while it auto-collects labelled samples. Ask **"How accurate would this be?"** and it quick-trains, tests itself on held-back samples, and answers in plain language ("I got 19 of 20 right") with a gallery of the ones that fooled it. **Test drive** the result live before committing, then **Turn it on** with one tap — it trains the final model, hot-swaps it in alongside the stock detector, and auto-creates the detection rule + alert for you. A **Keep teaching** loop lets you confirm/correct live alerts (✓/✗) so the skill improves on real-world cases, and skills can be shared to other MyMataSan devices as a passphrase-encrypted **.mmskill** file. "Spot anything unusual" learns from good-only footage using an image-embedding memory bank and alerts on deviations, running alongside object detection (its own per-camera slot). The old manual **Training** page is retired: model import/activate and object-class management moved to **Settings → AI**, and AI Detection rules created by a taught skill now carry a **"Taught"** badge.

## 2026-07-04 — core 1.49.2 (72bbe6a)

### Fixed

- **core**: THE root cause of the r450k download never working in a browser (while curl always did): with the Cloudflare Static Assets `not_found_handling: single-page-application`, browser *navigation* requests to non-asset paths are answered with the SPA index.html BEFORE the Worker runs — so clicking a download link navigated to /api/download/<id>, got the marketing page back (scrolled to top), and never downloaded. Non-navigation requests (the frontend's fetch('/api/downloads'), curl) still reached the Worker, which is why the list rendered and curl downloaded fine. Added `run_worker_first: ["/api/*"]` to the assets config so every /api/* request (navigation or fetch) is handled by the Worker first; all other paths are still served straight from assets with SPA fallback. Confirmed via a headless-browser click test (navigation to /api/download/<id> returned the page with no download event before the fix).
## 2026-07-04 — core 1.49.1 (9981984)

### Fixed

- **core**: r450k downloads still didn't work after removing target="_blank": the Worker's /api/download/<id> 302-redirected the browser to GitHub's signed CDN URL, and that cross-origin download-via-redirect behaves inconsistently in browsers (blank tab, or bouncing to the top of the page, without ever downloading). The Worker now proxies the asset and streams the bytes back as a SAME-ORIGIN response with Content-Disposition: attachment (Cloudflare streams the body, so nothing is buffered), which downloads reliably from a plain same-tab link in every browser. GitHub auth (needed for the private repo) is applied to the API call and dropped automatically when fetch follows the redirect cross-origin to the signed URL.

### Fixed

- **core**: Fixed `make build`/`make run`/`make test` (and friends) failing on Windows: GNU Make there runs recipes under a stripped MSYS /bin/sh that carries almost none of the Windows environment the Go toolchain needs — no USERPROFILE/APPDATA (Go can't locate GOPATH, its module cache, or its env file: "module cache not found: neither GOMODCACHE nor GOPATH is set") and no TMP/TEMP (Go tries to create its build work dir under C:\Windows and fails with "Access is denied"). The Makefile now reconstructs USERPROFILE/APPDATA/LOCALAPPDATA/TMP/TEMP from the real Windows user profile (resolved via `cygpath -F 40`, which works regardless of the ambient env) and threads them through every `go` invocation in run/run-go/build/build-go/test* via a `GOENV` variable, guarded to Windows only via `uname`; it is a no-op on Linux/macOS. Windows binaries also now get an explicit `.exe` suffix (Go only auto-appends it when it derives the output name itself, not with an explicit `-o` path). Separately, `build`/`build-go` now write the binary to `apps/<app>/bin/` (was the repo-root `./bin`) and a new `make stage` target (invoked automatically after build) copies `config.json` + `static/` + `ai/` alongside it, so `apps/<app>/bin/` is a self-contained, runnable bundle rather than a bare binary. `apps/*/bin/` was added to `.gitignore`.
- **mymatasan**: The in-app ffmpeg installer (Settings -> Runtime -> Decoder -> Download ffmpeg, and the first-run setup wizard's video-engine check) resolved its install directory as a CWD-relative `bin`, but a packaged Windows service runs with its working directory set to C:\Windows\System32, so the installer silently placed the downloaded ffmpeg binary there instead of anywhere the app could find it afterwards. It now installs under the writable `dataDir/bin` (an absolute path derived from deps.DataDir), mirroring how the self-contained Python/AI runtime already installs under `dataDir/pyruntime`.
- **core**: The r450k marketing site's Downloads page linked each release asset with `target="_blank"`, which opened a new blank tab and silently dropped the download instead of downloading the file — the Cloudflare Worker `/api/download` proxy behind it was already correct (verified end-to-end: 302 to a signed URL served as Content-Disposition: attachment). Links now use a plain same-tab anchor (no `target="_blank"`, and no `download` attribute — which browsers ignore/block once the same-origin endpoint redirects cross-origin); the server's Content-Disposition drives the in-place download without leaving the page.
## 2026-07-04 — mymatasan 1.79.6, core 1.47.3 (3748dca)

### Added

- **mymatasan,infra**: New Settings -> Backup & Recovery 'Configuration backup' panel and a first-run wizard recovery step that export and restore a portable, passphrase-encrypted .mmbackup of the app's configuration, so a fresh install can be brought up without reconfiguring. The bundle covers four independently selectable sections: Cameras (camera + ONVIF rows including stored credentials + recording configs), AI Detection (detection rules + the detection-class registry), Notifications (destinations + delivery settings, including Telegram/webhook/MQTT secrets), and App Settings (decoder/vision/capture + camera-health + machine-health). Because the file carries plaintext secrets that the normal API strips (json:"-" camera passwords, notification tokens), the engine reads entity rows directly and the whole file is encrypted with a user passphrase via a new portable Argon2id+AES-256-GCM primitive (infra/atrest.EncryptWithPassphrase/DecryptWithPassphrase) that is NOT tied to the machine's at-rest key, so a backup made on one host opens on another. Endpoints: GET /api/settings/backup/sections (row counts), POST /api/settings/backup/export|preview|restore (base64-in-JSON, admin-gated). Restore remaps auto-assigned primary keys (cameras insert first and build an old->new id map; recording configs, ONVIF rows and AI rules re-point to the new camera id; rules whose camera was not restored are skipped and counted), upserts the detection-class registry by name, and upserts settings by key; Replace mode wipes the selected sections first, Merge appends. The setup wizard's welcome step gains a 'Restore from backup' branch (upload + passphrase -> replace-restore -> restart to apply).

### Fixed

- **infra,mymatasan**: Hardened the graceful self-restart (apphost.Restarter, used by the UI restart button, backup restore, factory reset and self-update) so it can never spawn an unbounded storm of processes/console windows on Windows. Three fixes, all OS-aware: (1) the Windows self-relaunch now creates the detached child with CREATE_NO_WINDOW instead of DETACHED_PROCESS — DETACHED_PROCESS made Windows allocate a brand-new console window for the console-subsystem binary on every relaunch (the stray 'DOS command' windows), so a relaunch loop spammed windows until the machine had to be rebooted; (2) a cross-OS self-relaunch storm guard bounds relaunches to 5 within 60s (counted across the relaunch chain via KOPIV2_RESTART_GEN/KOPIV2_RESTART_T0 env, which the child inherits) and then stays DOWN with a clear log rather than looping, so a crash-on-boot or any immediate re-restart halts instead of running away; a window that elapses resets the count so ordinary restarts are never throttled; (3) a process running as a Windows service is now detected (svc.IsWindowsService) and treated as supervised, so it exits with restartExitCode for the SCM to relaunch instead of self-spawning a detached child that escapes the service and races a fresh service instance for the listen port.
- **infra,mymatasan**: Found and fixed the root trigger behind the 'nonstop DOS command windows' a user hit after restoring a backup and restarting: child processes (ffmpeg, ffprobe, python vision worker, nvidia-smi, tar, powershell) were spawned without suppressing their console window on Windows. A console child whose parent has no console of its own — the state a detached/relaunched app or a Windows service is in — gets a brand-new console window allocated on every spawn; the per-camera stream/recording pipeline retrying a failing ffmpeg (e.g. restored camera URLs that don't resolve on the new machine) then spammed windows without end. Added infra/procutil.HideWindow(cmd) — sets CREATE_NO_WINDOW on Windows, no-op elsewhere — and applied it to every exec.Cmd across infra/recording (capture, remux, clip extract, ffprobe duration/codec, TRIM/Optimize-Volume), infra/stream (live-view ffmpeg), infra/rtsp (MJPEG fallback, snapshots), infra/vision (one-shot + persistent detector workers), infra/externaltools (version probes), and the apps/mymatasan/services ffmpeg/python installers, LPR/training runners, and GPU detection. Complements the earlier apphost self-restart hardening (CREATE_NO_WINDOW on the relaunch + storm guard).
- **mymatasan**: Restoring a configuration backup now marks first-run setup complete, so the setup wizard no longer reappears after the restart — a restored machine is treated as already configured, matching what the user expects after applying a backup. Previously the setup-complete flag was intentionally excluded from the backup payload (it's host-local state), which left the wizard showing again until manually skipped. backupService.Restore now writes the setup.state runtime-setting after a successful restore (best-effort; surfaced via RestoreResult.SetupCompleted). The forced first-login password change is unaffected — it's a separate login gate, not the wizard — so skipping the wizard doesn't weaken the new-machine's admin credential. Also added a server-side log line to the capacity calibrate endpoint's estimate-build failure path (5xx detail is hidden from clients) so a 'Run Calibration -> internal server error' is diagnosable from the log, and a portable procutil smoke test asserting HideWindow keeps child stdio working.
- **infra,mymatasan**: Fixed the capacity 'Run Calibration -> internal server error' (and any object-detection) failure that appeared as 'persistent detector write failed: write |1: The pipe has been ended' with the request dying in ~100ms. Root cause: the persistent YOLO detector and the training runner spawned their Python child with cmd.Stderr = os.Stderr. When the app runs without a valid console — a relaunched/detached/Windows-service process, i.e. exactly the state after restarting the app to apply a restore — os.Stderr is an invalid handle, and inheriting it makes Python fail its stdio initialization and exit immediately, before it can read the first frame. The detector then hits a broken stdin pipe on its next write. Both spawns now redirect the child's stderr through a Go-created pipe drained to the app log, which is always valid regardless of the parent's console state and also surfaces the worker's ready/traceback lines in the structured log for diagnosis. Verified by running the real CUDA yolo worker end-to-end. Confirmed the earlier CREATE_NO_WINDOW change was not the cause.
- **mymatasan**: Fixed the object detector (and calibration) failing on a built/staged bundle with 'python.exe: can't open file ...\bin\apps\mymatasan\ai\yolo_worker.py: No such file or directory'. The detector's worker-script arg was a repo-root-relative path (./apps/mymatasan/ai/yolo_worker.py) passed raw to Python, which resolves it against the process working directory. From the `make build`/`make stage` bin/ bundle the working directory is bin/, so the path doubled to <bin>/apps/mymatasan/ai/... and the worker couldn't be opened; Python exited immediately and the persistent detector hit a dead stdin pipe (the calibration 500). The app now resolves vision.detector.args script paths to an absolute path against the app HomeDir (resolveDetectorScriptArgs), so the worker is found whether running from the repo root in dev (HomeDir=apps/mymatasan) or the staged bin/ bundle (HomeDir=exe dir, with ai/ staged alongside). Legacy repo-root-relative config values are recovered by basename in <HomeDir>/ai. The training script and base-model paths derive from the worker directory, so they follow automatically. Default config args changed to the HomeDir-relative 'ai/yolo_worker.py'.
- **mymatasan**: The first-run setup wizard could open partway through (e.g. on the Capacity/calibration step) instead of Welcome. The wizard persisted its step in localStorage and resumed it on every load, so a stale value from an earlier session — or a fresh install/reset opened in the same browser — reopened the wizard mid-flow. It now resumes a step ONLY across an in-app restart the wizard itself triggers (installing ffmpeg or GPU deps sets a one-shot 'setupResume' flag just before restarting, consumed once on the next load); any other first-run load starts at Welcome.
