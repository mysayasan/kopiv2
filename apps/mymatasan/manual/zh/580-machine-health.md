# 盯住机器本身

摄像机被监控着；跑它们的主机同样如此。**设置 → 主机健康**设定阈值，超限会以**主机健康**通知的形式出现
在信息流中。

## 监控什么 {#watched}

- **CPU**——持续负载。设备在正常运行中是 CPU 受限的，因此当您增加摄像机或换更大的模型时，这是第一个动
  起来的指标。
- **内存**——余量。检测模型常驻内存；多个活动模型会成倍占用。
- **磁盘**——特指**录像**所在卷的可用空间，而不是每一个挂载点。它是有硬后果的那一个。

## 磁盘警告为什么不一样 {#disk}

CPU 和内存压力会让体验变差。磁盘写满会**让录像停止**。

停止还是覆盖由您决定——参见[磁盘写满时](recording-configuration#disk-full)——但无论哪种，磁盘警告都是
当天就要处理的那一个。缓解措施只针对录像所在卷，这也正是存储路径不该放在系统盘上的原因：系统盘写满会
让整台设备下线，而不只是录像。

## 读懂持续的 CPU 警告 {#cpu}

几乎从来不是"买台更大的机器"。请先走一遍
[到底是什么在吃容量](storage-and-capacity#drivers)——实际上：

1. **检测**是不是被指向了主码流而不是子码流？这通常就是答案。
2. 有多少个**模型**处于活动状态？每一个都对每一帧做推理。
3. **基础模型**是不是比这套硬件想要的更大？
4. 实时画面的画面格是不是回退到了 **MJPEG** 而不是 WebRTC？
5. **人脸识别**是不是开在了并不需要它的摄像机上？

这五项里有四项是设置。修正它们通常比您当天下午能买到的任何硬件都能挤出更多余量。

## 设定阈值 {#thresholds}

请把阈值设成"通知出现就意味着要做点什么"。

一个每天下午繁忙时段都会触发的阈值，会训练所有人忽略主机健康通知——然后真正要紧的磁盘那条也被一并忽略
了。如果某个数值经常被突破而设备依然应付得来，那是阈值错了，不是机器错了。

## 容量，之前与之后 {#capacity}

同一个标签页上还有摄像机容量估算和**运行校准**。请在以下时机校准：

- 增加摄像机之前，让数字反映这套硬件；
- 更换基础模型或激活了另一个模型之后，因为计算前提变了；
- 硬件变更之后。

参见[存储与容量](storage-and-capacity#estimate)。

## 它不监控什么 {#limits}

- **网络吞吐。** 饱和的链路表现为摄像机抖动和画面格卡顿，而不是主机健康告警。参见
  [反复抖动的摄像机](camera-health#flapping)。
- **温度与风扇。** 请使用主机操作系统自身的监控；小型设备过热时会悄悄降频，而降频看起来正像"CPU 阈值
  老是触发"。
- **其他卷。** 只有录像卷有缓解措施。如果系统盘因别的原因在被填满，那要靠您的平台监控去发现。

## 它与其他部分的关系 {#related}

三个监控，三个问题，值得分清楚：

| 监控 | 回答 |
|---|---|
| [摄像机健康](camera-health) | 设备能访问到摄像机吗？ |
| **主机健康** | 机器跟得上吗？ |
| [存活与就绪](updates-and-restart#health) | 服务活着并且能提供服务吗？ |

同时盯住这三者的站点，几乎没有办法在无人察觉中损坏。
