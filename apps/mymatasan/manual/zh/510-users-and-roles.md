# 用户与角色

本地登录账号位于**设置 → 用户**。每个账号有一个角色，角色决定它能做什么。

## 三种角色 {#roles}

| 角色 | 可以 | 不可以 |
|---|---|---|
| **观看者** | 观看实时视频。看到告警发生过。修改自己的密码。 | 打开录像。确认、云台、喊话。设置中的任何内容。 |
| **操作员** | 以上全部，另加回放和下载录像、检索对象目击、确认告警、云台和喊话。 | 删除任何东西。修改规则、摄像机或设置。管理用户。 |
| **管理员** | 全部。 | — |

新账号默认为**操作员**。当某个账号应当只用于观看时，请把它改为观看者。

## 为什么操作员不能删除 {#evidentiary}

操作员之下的那条线正是整套模型的要点：**在事件现场的操作员，无法销毁该事件的录像。**

这才让这台录像机成为一份记录，而不只是一件方便的工具。它并不是在评价您雇用的任何人——它是让录像在事后
可以被信任的那条性质，包括被当班的那个人信任。

不要因为某次权限挡了路就把所有人都设成管理员。每一个能删除录像的账号，都让它的录像的分量少一点。

## 它在服务器上强制执行 {#enforcement}

每一个请求都会依据登录用户的角色被检查，而不只是写操作。被拒绝的区域是真的不可用，而不是藏在某个别人
能敲出来的网址后面。

矩阵是**默认拒绝**的：未被授予的一律拒绝。没有分配角色的用户什么都做不了，而对一个有人开了头却没弄完
的账号来说，这是唯一安全的解读。

## 创建账号 {#creating}

给它一个用户名、一个密码和一个角色。两个值得坚持的习惯：

- **一人一账号。** 共用登录会摧毁这里其他一切控制的审计价值。
- **能完成工作的最低角色。** 等有人撞了墙再提权，而不是一上来就人人管理员。

账号可以停用而不是删除，这通常正是有人离职时您想要的——删除会移除账号，停用则让名字仍与其历史相连。

## 密码 {#passwords}

每个人都可以在自己的会话中修改自己的密码。管理员可以重置任何人的密码。

引导管理员账号在首次登录时总是被强制改密——参见
[首次登录](first-sign-in#change-password)。重置后的密码最好标记为必须更改，以便本人自己设定。

多次失败后的锁定是自动的，对所有人生效，管理员也不例外——参见
[登录被锁定时](first-sign-in#lockout)。管理员不能缩短他人的锁定时间，这是有意的。

## 权限矩阵 {#matrix}

角色之下是服务器实际查阅的矩阵：受管的每一块 API 区域一行，写明每个内置角色在其中可以做什么。

内置角色在首次运行时由该目录播种。编辑矩阵是给那些确实需要三种角色表达不了的中间档位的站点用的——比
如"这里的操作员还可以清理诊断告警"。它是真正的安全控制，因此请有意识地改动，并在之后用该角色的真实账
号重新验证。

两个值得知道的行为：

- **最具体的匹配规则获胜**，而且规则不叠加。这正是用更窄的拒绝去从一条宽授权中挖掉一块的方式——设置可
  读，而其下的用户不可读。
- **默认值只会施加给完全没有权限的角色。** 一旦您调过某个角色，升级绝不会悄悄把它重置。

## 联合登录 {#federated}

mymatasan 只针对自己的本地账号做认证。它没有单点登录这条腿——那是 myidsan 和 myseliasan 的职责——所以
这里的账号就是全部账号。

请至少保留两个管理员账号。唯一的管理员已经离开、密码无人知晓的设备，只能靠在控制台重置管理员登录来
挽回。
