# 存储与容量

这是两个不同的问题，把它们混为一谈是安装效果不理想的常见根源：

- **这台机器能处理多少路摄像机？** 受 CPU、GPU 和内存限制。
- **它能把录像保留多久？** 受磁盘限制。

## 容量估算 {#estimate}

**设置 → 主机健康**中有摄像机容量估算，配置向导展示的是同一个数字。

它把 AI 检测、内存和录像建模为持续负载，报告主机可承载的摄像机数量以及**受限资源**——CPU、GPU、内存或
磁盘。实时画面被有意排除在外：它是按需的，而且没有人会同时看每一路摄像机。

它有三个置信等级，差别是实实在在的：

| 等级 | 依据 |
|---|---|
| **粗略估算** | 仅根据检测到的硬件。 |
| **由实时负载测得** | 由运行中摄像机的实际开销外推。 |
| **在本主机上校准** | 在这台机器上对检测器做的真实基准测试。 |

**在购买摄像机之前运行校准。** 它约需一分钟，最好在机器空闲时运行，而且远比规格表上的猜测有价值——真
实硬件上的真实吞吐与理论相差甚远。

## 到底是什么在吃容量 {#drivers}

按影响大致排序：

1. **检测码流的分辨率。** 把检测指向 4K 主码流而不是子码流，可能耗费数倍 CPU 而不增加任何检测结果。
   这是过载机器上第一个要检查的东西。参见[码流标签页](camera-properties#stream)。
2. **活动模型的数量。** 每个活动模型都对每一帧做推理。两个模型大约是两倍工作量——停用您不用的。
3. **基础模型的大小。** 从 nano 到 extra-large 跨度极大。在 CPU 或树莓派上，请留在 nano 或 small。
4. **MJPEG 实时画面。** 画面格显示"MJPEG 回退"而不是"实时"的墙，每路开销高得多。把摄像机编码改为
   H.264 能把这部分容量还回来。
5. **人脸识别**，在每一台启用了它的摄像机上。

请注意，这五项里有四项是配置而不是硬件。一台"扛不住"的机器，通常是其中之一没设对。

## 磁盘、保留期与摄像机数 {#disk}

磁盘限制的不是能跑多少路摄像机，而是能留多少历史。三个量相乘：

```
存储  ≈  摄像机数  ×  码率  ×  保留天数
```

改动其中任何一个，其他就跟着变。如果估算说磁盘是您的受限资源，您有四根杠杆：

- **加存储。** 诚实的办法。
- **降低录像码率或分辨率。** 便宜，代价是证据细节。
- **缩短保留期。** 便宜，代价是历史。
- **减少连续录像的摄像机数。** 有些摄像机确实只需要事件片段。

容量估算把录像视为滚动缓冲而不是硬墙：它不会因为磁盘小就宣布跑不了摄像机，而是把数量限制在大约一天最
低保留期上，并告诉您实际能达到的保留期。那才是可以拿来商量的数字。

## 依据审阅时间设定保留期 {#retention-policy}

最常见的存储错误，是为一个没人认真决定过的保留期去买磁盘。

请反过来问：**在这个站点，一起事件从发生到有人去审阅，实际要多久？** 如果是两周，那么七天保留期就意味
着"我们能看到吗"的答案经常是不能，而为摄像机花的每一分钱在那些事件上都没买到任何东西。

按那个数字去配磁盘。如果预算不够，就有意识地缩短保留期并告诉将来会来问的人，而不是在事件发生时才发现。

## 主机健康 {#machine-health}

**设置 → 主机健康**同时监控主机的 CPU、内存和磁盘，并在吃紧时产生主机健康通知。

请认真对待磁盘警告——它是有硬后果的那一个。磁盘停了录像就停，而缓解措施只针对录像所在卷，这也正是把存
储路径指向系统盘是个坏主意的原因：系统盘写满会让整台设备下线，而不只是录像。
