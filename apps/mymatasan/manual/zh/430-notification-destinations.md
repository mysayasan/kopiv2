# 通知送达目标

告警总会出现在应用内信息流中。**送达目标**是它们同时还会去的地方，好让人不必盯着屏幕也能知道。

在**设置 → 通知**中配置。

## 三种通道 {#channels}

**Webhook**——向您提供的 URL 发 HTTP POST。通用之选：任何能接收 JSON 的系统都能消费它。

**Telegram**——一个机器人令牌和一个聊天 id。在完全没有自有基础设施的情况下把告警送到手机的最快途径。
截图会以照片形式到达。

**MQTT**——代理地址和主题，附带客户端 id、QoS（0、1 或 2）、retain，以及完整 TLS（含 CA 与客户端证
书）。要与楼宇自控或既有运维总线集成，选它。

## 每个目标彼此独立 {#independent}

这正是让该功能有用的部分，也很容易被忽略。每个目标都有自己的：

- **最低严重程度**——一个下限。把上报路径设为仅"严重"，它在平常一整天都会保持安静。
- **接收哪些通知类型**——AI 检测、摄像机健康、主机健康、登录安全。一个都不勾表示全都要。
- **包含哪些检测字段。**
- **自定义字段。**
- **启用/停用**，无需删除。

于是一部手机只收"严重"，一个运维 MQTT 主题收全部，一个维护 Webhook 只收摄像机与主机健康、完全不收检
测。无论怎么配，应用内信息流始终完整显示全部内容。

## 载荷里有什么 {#payload}

对 AI 告警，您可以选择包含哪些检测字段：规则、摄像机、对象、置信度、时间戳、区域等等。

**车牌告警会自动包含**车牌号，以及在检测到时的车辆类型和颜色——消息文本和载荷中都有
（`plate`、`vehicleType`、`color`）。没有开关；您不必记得去启用它。

## 截图 {#snapshots}

两种投递方式：

- **内嵌**把图片嵌入——在 Webhook 与 MQTT 载荷中是 base64，在 Telegram 中是照片。收件人无需额外操作
  就能看到图。
- **仅链接**发送一个引用，由消费方自行取图。载荷小得多。

给人看用内嵌（带图的消息胜过十条不带图的），给机器以及那些不喜欢大 retain 载荷的 MQTT 代理用仅链接。

## 自定义字段与占位符 {#custom-fields}

自定义键值字段会被加入载荷，值中可以包含在发送时求值的占位符——摄像机名、规则名、时间戳等等。编辑器会
列出可用的记号，点击即可复制。

这正是让载荷去适配既有系统、而不是改写系统去适配载荷的办法：加上 `site: "north-depot"`，或把某个字段
塑造成您的自动化早已在读的那个键。与内置键同名的自定义字段会覆盖内置的，编辑器会提示。求值为空的记号
会被省略，而不是以空值发出。

## 按规则路由 {#routing}

默认情况下每条规则的告警都发往每个目标。在规则上选择特定目标即可收窄——参见
[创建检测规则](detection-rules#routing)。

有了按目标的过滤和按规则的路由，您就能表达一个站点真正需要的大部分策略：下班后的周界规则会把人叫醒，
白天的装卸区规则不会。

## 测试 {#testing}

**发送测试**会向订阅了该类型的目标投递一条系统通知。

配置时测一次，收件端有任何变动后再测一次。一条悄悄失效的投递路径，看起来和一个平静的夜晚一模一样。

请注意其中的相互作用：最低严重程度高于测试通知的目标，或者不接收系统通知的目标，将收不到这条测试。这
不是失败——那是您的过滤器在起作用。

## 告警没有被投递时 {#troubleshooting}

先确定坏的是哪一半：**这条告警在应用内信息流里吗？**

- **信息流里没有**——什么都没检测到。这是检测问题，不是投递问题；参见
  [通知](notifications#not-arriving)。
- **信息流里有但没投递**——那么依次检查：
  1. 该目标**启用**了吗？
  2. 它的**最低严重程度**允许这条告警吗？
  3. 它**接收这一类型**的通知吗？
  4. 该**规则**路由到它了吗？
  5. **发送测试**能到吗？如果能，说明传输没问题，挡住它的是过滤。

当某个目标暂时不可达时，投递会带退避重试；MQTT 会等待它的代理而不是在启动时丢弃消息——因此代理晚一点
起来并不会丢掉最初的那些告警。

## 通知保留 {#retention}

旧通知会按您设定的计划清理：保留天数、清理间隔，以及可选的"只清理已读"。设为零则关闭自动清理。

永久保留已读通知很少有用；录像和告警日志才是记录。间隔的改动在重启后生效。
