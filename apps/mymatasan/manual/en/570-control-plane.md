# Connecting to a control plane

A single appliance needs none of this. Skip the whole page unless you run **myseliasan**, the fleet
control plane that manages many recorders from one screen.

Everything here is in **Settings → Connectivity**, and the first-run wizard offers the same steps.

## What pairing gives you {#why}

A paired node can be managed from the control plane: its cameras, health and alerts roll up
centrally, and its pages can be opened from there over a secure tunnel — the operator's browser
never has to reach the node directly.

The node keeps running the same either way. Pairing adds central management; it does not move the
recording, the detection or the footage anywhere.

## The fleet key {#fleet-key}

Paste the **fleet key** generated by your control plane and save it. Minimum sixteen characters.

The key is what makes the node discoverable: discovery probes are signed with it, so **only a
control plane that holds the same key can see or adopt this node**. Without a key, the node does
not answer discovery at all.

That is the security property. Treat the fleet key like a password — anyone with it can find and
attempt to adopt your nodes on the local network.

Entering a new key replaces the existing one.

## The claim code {#claim-code}

Once the key is saved, **generate a claim code** and enter it in the control plane when adopting
this node. Codes expire, and the page shows when.

The two-step handshake is deliberate: the key says *which fleet you belong to*, the code says *and
I am consenting right now*. Neither alone is enough to adopt a node.

## Single parent {#single-parent}

A paired node is **locked to one control plane** and stops answering discovery probes altogether.

That is what prevents a second control plane on the same network from quietly adopting a node that
already belongs to somebody. There is no "paired to two fleets" state.

The Connectivity tab shows the paired parent and since when.

## Unpairing {#unpairing}

Two routes, and either works:

- **Release it from the control plane** — the normal way, and the one that leaves the control
  plane's own records tidy.
- **Unpair (self-drop)** here on the node — for when the control plane is gone, unreachable, or was
  decommissioned without releasing its nodes.

Either way the node becomes discoverable again and the previous parent loses access.

Self-drop is the escape hatch. Use it when the tidy route is not available, and remember to clean
up the stale entry on the control plane if it ever comes back.

## When adoption does not work {#troubleshooting}

1. **Is the fleet key saved on the node?** Without it, discovery is silent by design and the
   control plane will never see it.
2. **Do both ends have the same key?** A regenerated key on the control plane must be pasted here
   again.
3. **Is the node already paired?** A paired node does not answer discovery. Check the Connectivity
   tab, and unpair if it is bound to a control plane you no longer use.
4. **Has the claim code expired?** Generate a fresh one — they are short-lived on purpose.
5. **Is discovery reaching across the network?** It uses multicast, which routers do not forward
   by default. A node on a different VLAN from the control plane will not be discovered.

## Ports {#ports}

Fleet traffic uses its own ports, distinct from the web interface: discovery is multicast on the
local network, and the node-to-parent channel is mutually authenticated with certificates issued
by the fleet's own authority.

The node dials out to the parent rather than the reverse, so a node behind NAT works without
inbound port forwarding — which is usually the deciding factor for a remote site.
