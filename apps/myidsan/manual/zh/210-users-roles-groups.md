# 用户、角色与用户组

## 新账户什么都做不了 {#pending}

刚创建的账户——由管理员创建、自助注册，或通过已接入目录服务首次登录而产生——**完全没有角色**。它的主人看到的是
*等待放行*界面而不是工作区，在有人分配角色之前什么也做不了。

这是有意的。另一种做法，即继承某个默认访问级别，意味着一个自助注册的陌生人只要输入一个邮箱地址，就成了你身份
服务器的用户。

放行的方法：**用户**，找到该账户，设置它的角色，保存。对方界面上有**重新检查**按钮；他们不需要退出再登录。

> [!NOTE]
> 如果这个账户根本就不该存在，那就把它设为停用，而不是分配角色。删除它也可以，但会让审计线索指向一个谁也查不到的
> 账户。

## 角色决定的是菜单，不只是 API {#matrix}

一个角色就是一组规则，每条对应一个 API 路径前缀，各自授予 GET、POST、PUT 和 DELETE 中的若干项。**最长匹配前缀
胜出，没有规则就是拒绝。**

同一组规则也构建导航栏。给某个角色授予 `/api/user-credential` 的 `GET`，就是让**用户**为它出现；收回它，就是让它
消失。没有另一份需要同步维护的菜单配置——这正是为什么菜单不可能承诺一件服务器随后会拒绝的事。

两个后果：

- **同一台服务器上的两个人看到不同的导航栏。** 菜单短是系统在正常工作。如果同事能看到你看不到的界面，去比较角色，
  而不是比较浏览器。
- **宽泛的授权比看上去更宽。** `/api` 上的 `GET` 匹配产品中的每一条路径。请改为授予具体的前缀。

**超级管理员**完全绕过该矩阵。少数几个界面——用户、用户组、角色、RBAC、审计日志、备份与恢复、设置——无论矩阵怎么
写都仅限超级管理员，因为它们可以被用来提升权限、读取每一个用户名，或导出整个身份库。这些永远不下放。

## 用户组 {#groups}

用户组用于组织归属和层级：一个账户属于谁，挂在哪个父级下。它不是第二套权限系统——访问权来自角色。用户组最常见的
用途，是充当目录组映射的目标，让从你的域进来的人落到一个合理的位置；参见[接入目录服务](directory#mapping)。

## 端点与访问层级 {#endpoints}

**端点**界面是矩阵所针对的那份清单：产品提供的每一条 API 路径，以及它的层级。

- **AuthOnly** — 需要会话，然后由矩阵决定。几乎所有东西都是这一类。
- **Public** — 不需要会话。仅保留给必须在任何人登录之前就能工作的东西：登录端点本身、健康检查，以及本手册。
- **DevOnly** — 在开发构建之外不提供。

你很少需要动这个界面。它存在是为了让一条新端点不可能在悄无声息中可达，而不出现在管理员能看到的某个地方。

## 初始账户是应当退役的 {#handover}

只要出厂的超级管理员账户仍处于启用状态，工作区顶部就会有一条横幅这样提示。预期的最终状态是：真实的人以自己的身份
登录，初始账户被设为停用。

在那之前，审计日志中的每一项操作都归属于一个共享账户，这让整条线索远不如它本应有的那样有用——"superadmin 在
02:00 修改了一个角色"没有指出任何人。
