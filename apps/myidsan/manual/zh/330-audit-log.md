# 审计日志

审计日志是本服务器上所发生之事的只追加记录：每一次登录、每一次拒绝、每一次对"谁可以做什么"的更改。它可以被读取，
也可以按年龄淘汰，但产品中没有任何东西会编辑或删除其中的任何一条。

它**仅限超级管理员**，原因和它的 API 一样。这条线索指明了谁在何处做了什么，而在一台身份服务器上，它还会暴露哪些
用户名是存在的。

## 阅读它 {#reading}

**系统 › 审计日志**，最新在前。可按动作、结果（成功、拒绝、错误）、操作者和日期范围过滤；**导出 CSV** 使用同一组
过滤条件，所以你导出的就是你正在看的。

每一条记录都带有谁、做了什么、针对哪个目标、来自哪个地址、用什么浏览器，以及何时。没有操作者的记录不是缺陷：有些
事情确实是在无人登录的情况下发生的——参见[恢复标记](first-sign-in#reset-admin)。

## 动作名称 {#actions}

这些名称是一套封闭词表而不是自由文本，这正是它们值得用来过滤的原因。以下是值得一眼就认出的那些：

```spec
title : 你真正会用来过滤的动作名称
row login-failure `login.failure` : 一次凭据被拒绝。针对同一账户的一串这种记录是猜密码；来自同一地址、横跨许多账户的一串则是撞库喷洒。
row login-lockout `login.lockout` : 某个地址达到失败上限并被锁定。
row mfa-recovery `mfa.recovery_used` : 有人用掉了一个一次性恢复码。它被有意与普通登录分开记录——这是验证器已丢失或被接管的最强信号。
row mfa-admin-reset `mfa.admin_reset` : 某个账户的第二重验证被其主人以外的人清除，或被磁盘上的 RESET_MFA 标记清除。
row stepup-failure `stepup.failure` : 一个会话未能重新证明其凭据。这正是有人在试探被盗 cookie 时产生的记录。
row role-change `user.role_change` : 某人的角色被更改——本服务器上与权限最相关的一次修改。
row sso-refused `sso.refused` : 某个依赖方应用的登录被拒绝：重定向 URI 未注册、客户端未知、密钥错误，或授权码被重放。
row backup-export `backup.export` : 整个身份库以一个文件的形式离开了本服务器。
row audit-purge `audit.retention_purge` : 保留任务修剪了这条线索。它的存在，正是区分"被修剪过的日志"与"历史本来就从那里开始的日志"的依据。
```

除名称之外，认证类记录还会记下那个人是**怎么**进来的——本地、`ldap`、Kerberos、OIDC、社交登录，或恢复码——因此
"他们是怎么登录的？"无需回头对照当天的配置就能回答。

## 谁被放进了哪个应用 {#federation}

这是只有身份服务器才能回答的部分，而且很容易被忽略。

"这个账户被攻陷了——它触达了什么？"不是依赖方应用能回答的问题；每个应用都只看到一个会话凭空出现。MyIDSan 会针对
每次登录所打开的那个**应用**记录 `sso.authorize` 和 `sso.token_issue`，因此这条线索说明的不只是有人登录了，还有
那次登录换到了什么。

那些拒绝记录（`sso.refused`）可以说是更有用的一半。未注册的重定向 URI、未知的客户端和被重放的授权码，正是针对该
流程的攻击的样子，而只保存成功记录的线索是显示不出攻击的。当某个依赖方应用报告了一次它自己的日志解释不了的登录
失败时，原因就在这里。参见[接入应用](connecting-an-app#troubleshooting)。

## 保留多久 {#retention}

默认是**永久**。除非在 `config.json` 中打开保留策略，否则什么都不会被修剪，因为无限增长消耗的是磁盘，而缺失的
安全历史消耗的是一次调查。

打开之后，超过年龄上限的行会**先被归档到文件**，然后从表中移除，并且这次运行本身也会被记录。下限是 30 天——更短的
取值会被抬高到它，并在启动时给出警告，因为比这更短的线索能回答的东西非常有限。

> [!IMPORTANT]
> 归档文件以明文保存邮箱地址、来源地址和用户代理。它们被有意地不用本主机的静态加密密钥封存——一份归档如果其唯一
> 密钥只存在于它本该比之更长寿的那台机器上，那就不算归档——所以请相应地保护那个目录，并把它纳入你所备份的范围。

该归档与[备份与恢复](backup-restore)是分开的，后者根本不携带审计线索。
