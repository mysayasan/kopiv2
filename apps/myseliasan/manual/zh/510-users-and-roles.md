# 用户、角色与访问权限

## 新登录的人什么也拿不到 {#pending}

成功登录的人到达时**没有任何角色**，看到的是一个*等待授权*的页面，而不是控制平面。

这是刻意的，也是本页最重要的部分。身份验证证明的是这个人是谁；它并不说明这个人可以看到什么。在
管理员分配角色之前，新账号打不开任何东西——所以，一个会大方创建账号的身份提供方，也无法悄悄把你的
机队交到某人手里。

放行只需要一个动作：在 **Users** 列表里给他选一个角色。

## 管理用户 {#users}

列表会显示每个账号的 **Kind**（本地账号，还是通过 myidsan 联合登录的账号）、它的角色，以及是否处于
启用状态。

- **分配角色**——常规的放行操作。
- **Disable**——保留账号并收回其访问权限。对于已经离职的人，这才是你想要的；删除账号会连带丢失它
  做过什么的痕迹。
- **Make superadmin**——授予完全绕过权限。请节制使用，绝不要把它当作「本可以正经授权」的捷径。

## 退役初始超级管理员 {#handoff}

你第一次登录所用的账号是 **stock** 超级管理员，它不该长期留在服役状态。

创建一个真正的超级管理员账号，确认它可用，然后停用初始账号——这就是 **bootstrap handoff**。只有在
真正的超级管理员处于活动状态之后，控制平面才会提示你做这件事，所以提示出现的时机恰好是可以安全动手
的时候。

## 角色 {#roles}

角色分两种：不可删除的 **built-in** 角色，以及你自己创建的 **custom** 角色。

新角色以 **viewer** 起步：对机队和通知只读，外加对目前已接管的每个节点的 viewer 访问权限。从一个
自洽的起点收窄，好过从一片空白开始、然后一次一个投诉地发现缺口。

你可以重命名角色，也可以**复制**一个——这是做出「和操作员一样，再加上报告」的最快方式，不必手工重建。

## 访问权限：先用功能开关，必要时再用路径 {#access}

**Access** 以一组普通开关的形式授予角色控制平面能力——查看机队与摄像机、管理机队、通知、AI 助手。

**Advanced** 则为开关未覆盖的部分授予特定的 API 路径前缀和动词。大多数角色永远用不到它。

整个矩阵由两条规则支配：

- **最长匹配前缀优先。**
- **没有规则即拒绝。** 一个没有任何规则的角色被拒绝一切，也看不到任何菜单。

正因为默认拒绝，升级带来的新能力才不会悄悄地对所有人开放。

**超级管理员绕过所有检查**，因此它的矩阵按设计就是空的——没有什么要配置，也就没有什么会配错。

## 菜单和权限是同一回事 {#menus}

**Menu access** 用来切换某个角色能看到哪些导航区块，而每一个开关授予或收回的是**该区块 API 路径上的
GET 权限**。

这一点值得读懂而不是扫过：这里没有单独的「界面权限」。导航栏是由守卫 API 的同一份矩阵渲染出来的，
所以一个角色绝不可能看到它调用不了的页面；而隐藏菜单也不是叠加在真正安全措施之上的装饰——它**就是**
那个真正的措施。

实际后果是：如果有人看不到某个页面，请去授予对应能力，而不要去找什么显示开关，因为并不存在。

## 节点访问是另一个问题 {#node-access}

矩阵决定的是某人在**这个控制平面上**能做什么。它不决定某人在**某个节点上**能做什么。

节点访问是按节点授予的，级别取自节点自身——viewer（只读）、operator（读加有限写）或 admin（读写）。
接管了某个节点的那个角色，对它始终拥有完全访问权限。

请把两者分清楚：一个角色完全可以被允许看到这里存在某个节点，同时对那台设备本身没有任何访问权限；
对于一个只负责盯着机队、但不该重新配置摄像机的人来说，这恰恰是正确的。

## 当同事看不到某个页面或菜单时 {#troubleshooting}

菜单项缺失就意味着权限缺失——这里没有什么显示开关。按可能性排序：

1. **他还没有角色**——就是那个等待页面。分配一个。
2. **他的角色对那个路径没有规则**，而没有规则即拒绝。
3. **该区块的菜单开关是关的**，这和规则不存在是同一件事。
4. **他缺的是节点访问权限，而不是控制平面权限**——他能看到机队，却驱动不了那台设备。
5. **账号被停用了。**

以上每一种变更都会记入[审计日志](audit-log)。
